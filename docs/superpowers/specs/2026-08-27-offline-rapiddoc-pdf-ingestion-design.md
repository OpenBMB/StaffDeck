# StaffDeck 离线 RapidDoc PDF 解析设计

**日期：** 2026-08-27  
**状态：** 已确认设计方向，等待书面规格复核  
**适用范围：** StaffDeck 所有 PDF 上传、导入和文件读取入口

## 1. 背景与问题

StaffDeck 当前通过 `pypdf` 提取 PDF 自带的文字层。该方式适用于由 Word 等软件导出的电子 PDF，但扫描型 PDF 的页面通常只有图片，没有可搜索文字层，因此解析结果为空。审核项目中的实际失败样本已经证明这一点：失败文件可以正常打开，但页面文字无法由 `pypdf` 提取。

此前新增的 `PDF_TEXT_LAYER_MISSING` 错误提示只能说明原因，不能让 StaffDeck 直接读取扫描文件。本设计增加完全离线的结构化文档解析能力，使用户上传扫描 PDF 后无需在外部软件中执行 OCR 或替换文件。

## 2. 目标

1. 扫描 PDF 上传后在 StaffDeck 内自动完成 OCR、版面恢复和表格结构识别。
2. 解析能力覆盖审核材料、知识库、对话附件及技能/文件工具等全部 PDF 入口。
3. 审核材料和模型推理全程留在本机，不调用第三方 OCR 云服务。
4. 原生文字 PDF 继续使用快速解析路径，不承担不必要的 OCR 开销。
5. 统一输出包含页码、阅读顺序和 Markdown 表格的文本，供现有分块、检索和审核报告流程使用。
6. OCR 失败时保留原始文件、错误原因和重试能力，不产生“处理成功但文本为空”的假成功状态。
7. 在正式启用前使用真实审核材料验证资源占用、速度和识别质量。

## 3. 非目标

1. 不接入 CamScanner、TextIn 或其他第三方云 OCR API。
2. 不安装 RapidDoc 的 GPU、PyTorch、VLM 或公式识别运行栈。
3. 不承诺手写字、印章遮挡、严重模糊、缺页或破损页面达到 100% 识别准确率。
4. 不在本阶段实现人工标注、OCR 模型训练或模型微调。
5. 不改变现有知识检索、材料分块和审核报告生成的业务规则；本设计只改造其上游文档解析来源。

## 4. 方案选择

采用 **RapidDoc 精简 CPU 方案**，但通过 StaffDeck 自有适配层隔离第三方接口。

RapidDoc 提供 OCR、版面分析、阅读顺序和表格识别，结构化能力优于只组合 RapidOCR 与 RapidTable。官方完整 CPU 安装会同时引入 ONNX Runtime 和 OpenVINO，并包含与本项目无关的公式、演示或多格式处理能力，因此 StaffDeck 不直接采用完整默认配置。

精简配置如下：

- 推理引擎：ONNX Runtime CPU。
- OCR：启用 RapidOCR。
- 版面识别：启用 PP-DocLayout 系列 ONNX 模型，最终型号由真实材料基准测试确定。
- 表格识别：启用有线/无线表格分类及轻量 ONNX 表格模型。
- 阅读顺序：启用。
- 公式识别：关闭。
- 表格内公式：关闭。
- 图片提取：关闭。
- 复选框识别：默认关闭，因为官方说明存在误检风险；后续只有真实审核样本证明收益大于风险时才单独设计启用。
- OpenVINO、Torch、CUDA、VLM：不安装。

如果隔离验证发现 RapidDoc 无法在不安装 OpenVINO 的情况下稳定运行，或者未达到第 13 节门槛，则不把 RapidDoc 写入生产依赖，回退到已评估的 RapidOCR + RapidTable 适配器。回退只更换解析引擎实现，不改变上层接口和数据流。

## 5. 总体架构

新增统一的文档解析服务，业务代码不再直接调用 `pypdf` 或第三方 OCR 包。

```text
上传/读取 PDF
      |
      v
DocumentExtractionService
      |
      +-- PDF 快速探测器：页数、文字覆盖率、加密/损坏状态
      |
      +-- NativePdfExtractor：原生文字充足时使用 pypdf
      |
      +-- StructuredPdfExtractor：扫描或混合 PDF 使用 RapidDoc
      |
      v
DocumentExtractionResult
      |
      +-- Markdown 全文
      +-- 页级结果与页码
      +-- 表格结构
      +-- 解析方法与质量元数据
      +-- 警告和错误代码
      |
      v
现有分块、知识库、审核证据、对话附件和文件工具
```

第三方 RapidDoc 只能在 `StructuredPdfExtractor` 内导入。其他模块依赖 StaffDeck 定义的协议，避免 RapidDoc API 升级扩散到整个项目。

## 6. 统一接口

统一解析服务返回结构化结果，而不是只返回 `(text, format)`：

```python
@dataclass(frozen=True)
class ExtractedPage:
    page_number: int
    markdown: str
    method: Literal["native", "ocr"]
    confidence: float | None
    warnings: tuple[str, ...]


@dataclass(frozen=True)
class DocumentExtractionResult:
    markdown: str
    document_format: str
    method: Literal["native", "rapiddoc", "hybrid"]
    pages: tuple[ExtractedPage, ...]
    warnings: tuple[str, ...]
    engine_version: str | None
```

对现有调用方保留兼容包装 `extract_text(filename, content) -> tuple[str, str]`，其内部调用新服务并返回 Markdown 与文件类型。需要展示状态、置信度或诊断信息的新流程直接使用结构化接口。

## 7. PDF 路由规则

1. 校验文件签名、加密状态、页数和可读取性。
2. 使用 `pypdf` 按页提取原生文字并计算页级有效文字量。
3. 所有页面均有足够文字时，返回原生快速结果。
4. 任一页面无文字，或文档有效文字覆盖率低于配置阈值时，将整个 PDF 交给 RapidDoc 的 `auto` 解析模式。RapidDoc 对文字页优先读取原生文本，对扫描页执行 OCR。
5. RapidDoc 返回空文本、页数不一致或发生异常时，任务标记失败，不用原生空结果覆盖此前内容。
6. PDF 之外的 TXT、Markdown、HTML 和 DOCX 继续沿用现有解析器，不进入 RapidDoc。

阈值是 StaffDeck 配置项，首版默认值在真实样本基准测试中确定并写入测试，不使用未经验证的魔法数字。

## 8. 全入口覆盖

以下入口统一迁移到 `DocumentExtractionService`：

1. 审核项目材料上传、替换和重试。
2. 知识库文档上传与版本处理。
3. 对话附件保存和文本提取。
4. Harness 文件系统的 PDF 读取与文档提取能力。
5. 其他直接调用 `app.knowledge.parser.extract_text` 的导入流程。

迁移后禁止在业务模块内新增第二套 PDF OCR 逻辑。代码扫描测试会检查已知 PDF 入口是否仍直接实例化 `PdfReader`；底层探测器和明确的测试夹具除外。

## 9. 后台任务与状态

OCR 可能持续数十秒到数分钟，不能占用上传请求直到完成。

- 上传请求只负责保存原始文件、创建持久化处理记录并提交后台任务。
- 状态统一为 `pending -> processing -> succeeded | failed`。
- 处理记录持久化解析方法、引擎版本、页数、字符数、开始时间、完成时间、警告和错误代码。
- 前端轮询现有材料/知识版本状态，显示“等待解析”“OCR 识别中”“结构化处理中”“处理成功”“处理失败”。
- 服务重启后发现长时间停留在 `processing` 的任务时，将其恢复为可重试状态，不假定内存队列仍然保存任务。
- 同一文件哈希、同一引擎版本和同一配置的成功结果可以复用，避免重复 OCR。
- 默认每台 PC 同时只运行一个结构化 OCR 任务，防止多任务争用内存；原生文字提取不受该限制。

现有进程内 `AsyncJobQueue` 可以用于执行，但任务事实以数据库状态为准，不能只保存在内存中。

## 10. 模型与依赖生命周期

- Python 版本保持 3.11 或更高。
- 生产依赖采用经过隔离验证的固定版本范围，不使用无上限的最新版本。
- 模型目录通过 `STAFFDECK_OCR_MODELS_DIR` 配置；默认位于 StaffDeck 可写数据目录，不写入 Python site-packages。
- 提供独立的模型准备命令，在安装或升级阶段下载、校验 SHA256 并记录清单。
- 正常上传和解析阶段禁止隐式联网下载模型。模型缺失时返回 `OCR_MODEL_MISSING`，提示管理员运行准备命令。
- 多台 PC 分别准备模型；后续可将经过校验的模型目录离线复制到其他 PC。
- 模型清单记录名称、来源、版本、SHA256 和许可证，保证可复现部署。

## 11. 输出、检索与全文保证

- 输出使用 UTF-8 Markdown。
- 每页以稳定页码标题分隔，保证引用能够追溯到原 PDF 页。
- 表格输出为 Markdown 或内嵌 HTML，不能只拼接单元格文字。
- 分块继续基于最终 Markdown，但不得跨越页级来源边界而丢失页码信息。
- `characters`、覆盖率和审核证据统计以最终结构化文本为准。
- 原始 PDF 始终保留；OCR 输出是派生数据，可以重新生成。
- “全文保证”定义为系统处理所有可读取页面并保存其解析结果，不等同于 OCR 绝对无误。低置信度、空白页和处理警告必须可见，不能被静默丢弃。

## 12. 错误处理

新增或统一以下错误代码：

- `OCR_DEPENDENCY_MISSING`：RapidDoc 或 ONNX Runtime 未安装。
- `OCR_MODEL_MISSING`：本地模型不存在或校验失败。
- `OCR_PDF_ENCRYPTED`：PDF 加密且无法读取。
- `OCR_PDF_CORRUPT`：PDF 损坏或页渲染失败。
- `OCR_TIMEOUT`：超过单任务时间限制。
- `OCR_EMPTY_RESULT`：OCR 完成但没有可用文字。
- `OCR_PAGE_PARTIAL_FAILURE`：部分页面失败；任务不标记为完整成功，并列出失败页。
- `OCR_RESOURCE_LIMIT`：预计页数、像素或内存超过安全限制。

日志只记录文件标识、页码、耗时、状态和技术错误，不记录审核材料全文。前端显示可执行的中文提示，但不暴露本机绝对路径或堆栈。

## 13. 验收门槛

RapidDoc 只有在真实材料隔离验证全部通过后才进入生产依赖：

1. 新增依赖、模型和缓存的稳定磁盘占用不超过 2 GB。
2. 单任务峰值内存不超过 4 GB。
3. 当前测试 PC 上，普通 20 页、约 300 DPI 的审核扫描件处理时间不超过 3 分钟。
4. 清晰中英文印刷文字的人工抽样完整率达到 98% 左右。
5. 关键审核表格的行列对应关系人工抽样正确率不低于 90%。
6. 每个输入页面在输出中都有页级结果、空白页标记或明确失败记录，不允许静默漏页。
7. 模型准备完成后，断网环境可以完成启动和解析。
8. 原生文字 PDF 的解析性能和文本结果不得出现明显回退。

“98% 左右”用于筛选 OCR 路线，不代表对每份材料的法律或审核准确性保证。最终审核报告仍应对关键名称、数值、日期和结论进行证据核对。

## 14. 测试策略

按 TDD 实施，每项行为先写失败测试：

- 单元测试：原生 PDF 路由、扫描 PDF 回退、混合 PDF、空结果、模型缺失、超时、页级失败、结果合并。
- 适配器契约测试：使用假引擎验证业务层不依赖 RapidDoc 具体类型。
- 入口测试：审核材料、知识库、对话附件和 Harness 文件读取均调用统一服务。
- API 测试：上传立即返回待处理状态，后台完成后状态和字符数更新。
- 前端测试：OCR 状态、警告、失败原因和重试操作。
- 真实文件验收：使用现有成功与失败 PDF，记录页数、字符数、耗时、峰值内存和人工抽样结果。
- 离线测试：阻断网络后加载已准备模型并解析扫描 PDF。
- 回归测试：现有审核、知识库、聊天附件、构建和启动脚本测试全部通过。

真实审核文件只用于本机人工验收，不提交到 Git。自动化测试使用无敏感信息的最小扫描 PDF 夹具。

## 15. 发布与回退

1. 先在隔离环境安装 RapidDoc 精简依赖并运行真实材料基准，不修改生产虚拟环境。
2. 达标后固定依赖和模型清单，再实现统一适配器与后台任务。
3. 通过配置开关 `STAFFDECK_STRUCTURED_PDF_ENABLED` 灰度启用；原生路径始终保留。
4. 现有失败材料由管理员点击重试，重新进入 OCR 队列，不要求替换文件。
5. 如出现资源或质量问题，关闭配置开关即可恢复原生 PDF 路径；原始文件和旧提取结果不删除。

## 16. 已知风险

- RapidDoc 是较新的开源项目，第三方 API 和模型配置可能变化，因此必须通过适配层和版本固定隔离。
- 官方完整 CPU 路线默认使用 OpenVINO；ONNX Runtime 精简路线需要先验证所有启用模块都能稳定工作。
- 跨页表格、复选框、印章遮挡和复杂多栏版面仍可能识别不完整。
- 多台性能差异较大的 PC 会产生不同耗时，验收结果只能代表测试硬件；发布文档必须给出最低硬件建议。
- OCR 提升可检索性，但不能代替审核人员对关键证据的复核。

## 17. 设计决策摘要

- 覆盖全部 PDF 入口，而不是只修审核项目。
- 使用 RapidDoc 的结构化能力，但采用 ONNX Runtime 精简 CPU 配置。
- 原生文字优先，扫描或混合 PDF 自动回退到结构化 OCR。
- 公式、VLM、GPU、OpenVINO 和默认复选框识别不进入首版。
- 使用统一适配器、持久化后台状态和固定模型目录。
- 先以真实材料和明确门槛验证，再决定是否写入生产依赖。
- 不达标时回退 RapidOCR + RapidTable，不牺牲上层接口稳定性。
