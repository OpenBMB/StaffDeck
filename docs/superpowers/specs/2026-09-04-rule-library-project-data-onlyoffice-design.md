# StaffDeck 规则库、项目数据域与 ONLYOFFICE 智能文档工作台设计规格

日期：2026-09-04
状态：设计已逐节确认，待规格文件终审
适用范围：认证项目、知识库、规则库、RapidDoc/OCR、报告生成 SOP、ONLYOFFICE 集成与多人协作部署

## 1. 摘要

本设计把 StaffDeck 的认证项目从“上传材料后由数字员工生成报告”扩展为受控的认证项目文档工作台。核心不是简单嵌入一个在线编辑器，而是建立以下闭环：

```text
原始材料
   ↓ 全文解析、OCR、证据定位
项目数据域 ← 候选值、人工确认、版本与冲突
   ↓ 已批准事实
工作文档 ↔ ONLYOFFICE 保存点同步
   ↓ 规则检查、知识依据、人工复核
定稿归档
```

同时将“知识库”和“规则库”明确分离：

- 知识库保存法律法规、标准、认证规则及机构制度全文，负责动态检索和提供引用依据。
- 规则库保存项目执行时必须遵守的结构化要求，负责流程控制、校验和生成约束。
- 项目数据域保存项目内已批准的共享事实，是跨文档同步的唯一中枢。
- AI 只能提取候选、提供建议和生成草稿，不得静默改写权威数据或定稿文件。

## 2. 已核实的当前基础

根据当前仓库代码和既有设计文档，以下能力已经存在或正在当前工作区实现：

- 后端为 Python 3.11+ FastAPI，前端为 React/TypeScript。
- 认证项目继续使用代码模型 `AuditCase`、项目标识 `audit_case_id` 和 `/api/audit-cases` 路径。
- 已有项目、成员、材料、材料分块、证据台账、报告版本和项目事件模型。
- 已有管理员认证项目页面、项目详情页面和聊天会话项目绑定能力。
- 已有 RapidDoc/OCR 文档摄取路线、长文档分块和覆盖率机制。
- 已有知识库、知识库版本、知识文档及混合检索配置能力。
- Harness v2 已有 SOP 节点、能力清单、知识范围和任务请求编译机制，可作为规则上下文接入点。
- 当前仓库指南把 SQLite 作为已支持的生产迁移路径；PostgreSQL 尚不能视为已完成支持。
- 当前代码库中尚未发现正式的规则库领域模型或完整 ONLYOFFICE 生产集成。

以上“存在”不等于全部已经通过本设计的验收标准。本规格只定义目标边界，实施时仍需按阶段验证现有功能的实际状态。

## 3. 待核实事项

以下事项在进入对应实施阶段前必须单独核实，不能根据演示、会议材料或产品宣传直接认定：

1. 采用的 ONLYOFFICE 版本、许可范围、并发限制、插件能力和商业分发条件。
2. Community Edition 是否足以满足计划中的内容控件交互和部署规模。
3. 真实认证模板在 ONLYOFFICE 与 Microsoft Word 往返编辑后的格式保真度。
4. PostgreSQL 对当前 SQLModel、启动迁移和 SQLite 专用 SQL 的兼容改造量。
5. 中心服务器的并发规模、文件容量、备份周期和恢复目标。

## 4. 问题定义

当前模式主要存在以下业务风险：

1. 知识依据和执行规则混在一起时，系统容易把“检索到的参考内容”误当成“当前项目必须执行的规则”。
2. 多份审核文档重复保存企业名称、日期、场所、范围和人员等信息，修改后容易不一致。
3. 直接从一份文档向另一份文档复制数据会形成循环覆盖、来源不明和历史不可追溯。
4. 扫描 PDF 或长文档即使上传成功，也不代表全文已经解析或报告生成确实覆盖了全部材料。
5. 把全部材料一次性放入大模型上下文，不能证明模型逐字处理，也无法稳定获得可审计结果。
6. AI 如果可以直接修改正式文档或已批准字段，会把抽取错误迅速传播到多个文件。
7. 多人编辑时若采用“最后保存者获胜”，会静默丢失其他人的修改。

## 5. 目标

本设计实现：

1. 管理员按流程、管理体系、审核类型和信息域维护规则库。
2. 项目创建时推荐适用规则，并由项目管理员明确选择和锁定规则版本。
3. 原始材料只上传一次，完成全文处理、证据定位和覆盖检查。
4. 项目共享事实集中保存在项目数据域，并保留候选、批准、冲突和历史版本。
5. 多份工作文档通过项目数据域同步，不发生直接文档到文档复制。
6. 在 StaffDeck 内嵌 ONLYOFFICE，支持保存、版本、内容控件绑定和保存点同步。
7. 报告按章节生成，每个结论可以追溯到项目材料、知识依据和命中规则。
8. 冻结和归档文件不可被静默修改，所有变更均可审计。
9. 使用现有 StaffDeck 账号、租户和项目成员体系，不另建一套身份系统。

## 6. 非目标

首期不实现：

- 每输入一个字符就实时同步所有文档。
- 让 AI 自动批准关键事实或绕过强制规则。
- 用向量检索决定哪些规则必须执行。
- 把每一句自然语言都拆成结构化字段。
- 自动修改冻结或归档文件。
- 通过增加模型上下文长度代替材料覆盖和证据追踪。
- 首期拆分微服务或引入图数据库。
- 在未经适配和验证的情况下直接宣布 PostgreSQL 已受支持。
- 未完成许可评审就把 ONLYOFFICE 集成用于正式生产。

## 7. 方案比较与选择

### 7.1 方案 A：项目数据域中枢（采用）

```text
文档 → 字段候选 → 项目数据域 → 同步预览 → 其他工作文档
```

优点：权威来源唯一、冲突可见、版本可追溯、适合规则校验和多人协作。
缺点：需要建立字段模式、内容控件绑定、候选审批和同步任务。

### 7.2 方案 B：主文档带动其他文档（不采用）

指定一份主文档，其他文件从中读取数据。

优点：初期实现较快。
缺点：主文档格式变化会影响全局；复杂数组和多来源事实难以表达；其他文档产生的新事实仍需要回写主文档，容易形成双向冲突。

### 7.3 方案 C：文档之间直接互相同步（拒绝）

优点：表面上路径最短。
缺点：容易形成循环回写、最后写入覆盖、来源丢失和不可复现，无法满足正式审核文件的审计要求。

因此采用方案 A。

## 8. 不可破坏的设计原则

1. 文档是事实的呈现载体，不是跨文档共享事实的唯一来源。
2. 跨文档共享只能经过项目数据域。
3. AI 写入候选区，批准人写入权威区。
4. 知识库提供依据，规则库控制执行，两者不混为同一种检索对象。
5. 所有关键字段均具有类型、范围、状态、版本、来源和审批记录。
6. 所有文档均具有区域、状态、版本、哈希和生命周期。
7. 冻结或归档文档绝不被静默修改。
8. 数据冲突不得通过“最后保存者获胜”自动消解。
9. “证据不足”与“结论错误”必须分别表达。
10. 先完成少量真实模板闭环，再扩大字段、文档和自动化范围。

## 9. 总体架构

采用“现有 StaffDeck 模块化扩展＋独立 ONLYOFFICE Document Server”的低风险架构。

### 9.1 StaffDeck 内部模块

- 认证项目模块：项目、成员、材料、报告和事件。
- 项目数据域模块：字段定义、字段值、候选、版本、来源和冲突。
- 规则库模块：规则集、规则版本、原子规则、发布和测试。
- 规则执行模块：流程前检查、输出后检查、结果和例外放行。
- 文档工作台模块：文档三区、模板绑定、编辑配置、版本和同步。
- 证据模块：RapidDoc/OCR、全文分块、材料覆盖账本和引用定位。
- AI 编排模块：按流程节点组装项目数据、规则、材料证据和知识证据。
- 后台任务模块：解析、OCR、向量化、同步、批量规则检查和失败重试。

### 9.2 外部或独立运行组件

- ONLYOFFICE Document Server：文档编辑、协作及保存回调。
- 模型服务：生成模型、Embedding 模型和 Reranker 模型继续独立配置。
- 数据库：当前阶段保持 SQLite 兼容；多人生产化阶段专项适配 PostgreSQL。
- 文件存储：通过统一存储接口兼容现有本地文件，后续可扩展 MinIO 或其他对象存储。

## 10. 知识库与规则库边界

### 10.1 知识库

知识库保存完整来源文件，包括：

- 法律法规；
- 国家、行业和团体标准；
- 认证规则；
- 认可规范；
- 认证机构制度和作业文件；
- 其他需要作为依据引用的正式文件。

运行时采用 BM25、向量召回和 Reranker 的混合检索，输出必须包括来源文件、版本、位置和原文片段。知识检索结果是证据或参考依据，不自动成为项目强制规则。

普通项目默认继承所绑定数字员工的知识范围，即使用现有 `knowledge_scope_mode=agent_default` 语义；项目创建页面不再要求用户重复勾选同一批知识库。只有确有隔离或专项依据需求时，管理员才切换到 `custom` 并显式覆盖知识范围。项目页面始终显示本次实际生效的知识库及版本来源，避免“继承后不可见”。

### 10.2 规则库

规则库保存经过管理员编制的结构化执行要求。规则不是把知识文档复制一遍，而是引用知识来源并表达“在什么条件下、检查什么对象、如何判断、产生什么结果”。

规则运行时按以下结构化条件精确筛选：

- 租户；
- 管理体系；
- 审核类型；
- 流程阶段；
- 信息域；
- 文档类型；
- 字段或章节；
- 项目绑定的规则版本。

规则库不依赖向量检索来猜测适用性。语义模型可以辅助管理员起草或测试规则，但不能自行决定强制规则是否适用。

### 10.3 规则引用知识来源

每条规则可引用一个或多个知识库条款：

```text
rule → knowledge_base_version → document → page/section/chunk
```

知识文件更新不会自动改写已发布规则。管理员创建新版规则时应显示来源变化和影响范围。

## 11. 规则库数据模型

建议新增以下领域实体，具体表名在实施计划中结合现有命名规范确定。

### 11.1 `RuleSet`

表示可管理的规则包：

- `id`、`tenant_id`、名称、说明；
- 适用管理体系和审核类型；
- 业务域、所有者和标签；
- 当前发布版本；
- 草稿、已发布、已停用状态。

### 11.2 `RuleSetVersion`

表示不可变的发布快照：

- 规则集 ID、版本号、发布说明；
- 生效和失效时间；
- 发布人、发布时间；
- 内容哈希和来源版本快照。

已发布版本不原地修改。修订必须创建新版本。

### 11.3 `RuleDefinition`

表示原子规则：

- 稳定规则键和显示名称；
- 适用流程节点、信息域、文档类型、字段或章节；
- 触发条件和校验表达式；
- `mandatory`、`warning`、`guidance` 执行等级；
- `deterministic`、`model_assisted` 执行方式；
- 输入要求、证据要求和失败提示；
- 知识来源引用；
- 可否例外放行及所需角色。

### 11.4 `ProjectRuleBinding`

表示项目绑定的明确规则版本：

- 项目 ID；
- 规则集版本 ID；
- 来源为系统推荐或管理员手动选择；
- 启用状态和优先级；
- 绑定人、绑定时间；
- 迁移前后版本及迁移原因。

项目启动后不自动跟随规则库最新版。系统只提示存在新版，由项目管理员查看差异和影响后决定是否迁移。

### 11.5 `RuleEvaluation` 与 `RuleException`

规则执行结果至少保存：

- 项目、规则版本、流程节点和目标对象；
- 输入数据版本和证据引用；
- 通过、失败、警告、待人工确认或不可判定；
- 执行器或模型版本；
- 执行时间和请求标识；
- 例外放行人、原因、依据和时间。

## 12. 规则执行等级

### 12.1 强制规则

- 仅确定性、证据边界清晰的规则可以直接阻止流程推进或文档定稿。
- 普通编辑者不能绕过。
- 指定复核人可按配置例外放行，但必须填写原因和依据。

### 12.2 警告规则

- 不阻止继续操作。
- 必须显示风险并记录用户的确认或处理结果。

### 12.3 指导规则

- 用于约束 AI 生成、提示审核员和提供修订建议。
- 不直接阻断流程。

### 12.4 模型辅助判断

语义模糊、需要综合判断或依赖自然语言理解的结果不得直接作为强制阻断结论。模型输出只能为“建议通过、建议不通过、无法判断”，并交由人工确认。

### 12.5 规则冲突与优先级

- 同一项目同时命中互相矛盾的强制规则时，系统必须阻止对应动作并要求管理员处理规则绑定，不能自行择一执行。
- 更具体的适用范围可以覆盖一般性规则，但覆盖关系必须在规则版本中显式声明并通过发布校验。
- 项目级规则不得静默削弱法律法规、认可规范或机构强制规则；允许例外时仍按强制规则放行流程处理。
- 规则优先级只决定检查和展示顺序，不能单独作为消除实质冲突的依据。
- 规则发布前测试必须覆盖重复规则、循环覆盖、缺失来源和不可满足条件。

## 13. 项目数据域

项目数据域是项目内共享事实的唯一中枢，不等同于知识库，也不等同于某一份文档。

### 13.1 字段范围

建议支持：

- 组织级：法定名称、注册地址、统一社会信用代码；
- 项目级：管理体系、审核类型、认证范围、适用标准；
- 审核活动级：审核日期、审核组、场所和日程；
- 文档级：文档编号、版次、签发信息；
- 结构化集合：多场所、审核组成员、能源种类、能源绩效参数、审核发现和不符合项。

### 13.2 稳定字段键

字段键应表达业务语义，例如：

```text
organization.legal_name
organization.registered_address
certification_project.scope
audit_event.start_date
audit_event.team_leader
energy.review.significant_energy_uses
document.number
```

禁止使用依赖模板位置的键，例如“字段1”“表格第二行”或“审核计划中的日期”。

### 13.3 字段记录

每个字段值至少保存：

- 字段键、类型、范围和值；
- 候选、待验证、已验证、已批准、已替代或已拒绝状态；
- 当前版本和期望版本；
- 来源文件、文件版本、页码、段落、表格单元格或内容控件；
- 证据片段和提取方法；
- 提交人、批准人及时间；
- 置信度和校验结果。

### 13.4 状态流转

```text
extracted / proposed
        ↓
pending_validation
        ↓
validated
        ↓
approved
        ↓
superseded
```

候选也可以进入 `rejected`。机器验证通过不等于人工批准。

### 13.5 冲突处理

- 已批准值高于未批准候选。
- 多个来源提出不同值时并列保存，不自动覆盖。
- 打开文档后项目值发生变化时，保存时显示版本冲突。
- 空值、OCR 失败或解析失败不得覆盖已有批准值。
- 使用乐观锁防止并发覆盖。

## 14. 项目文件库三区

### 14.1 原始材料区

- 保存上传原件及哈希。
- 不允许在线覆盖原件；替换产生新材料版本。
- RapidDoc/OCR 结果作为衍生数据保存，不改变原文件。
- 可参与证据检索，不参与跨文档回填。

### 14.2 工作文档区

- 保存由模板生成或人工创建的可编辑文档。
- 允许 ONLYOFFICE 编辑、版本化、规则检查和保存点同步。
- 只有本区域文档可以接收项目数据域的同步更新。

### 14.3 定稿归档区

- 文档冻结后只读。
- 保存文件哈希、定稿人、规则快照、项目数据快照、知识版本和证据清单。
- 后续修改必须从定稿版本创建新修订，不允许原地改写。

### 14.4 文档状态

```text
draft → in_review → approved → frozen → archived
```

状态转换由权限和规则门禁控制。

## 15. 模板与内容控件

新模板优先使用 DOCX 内容控件绑定稳定字段键。每个绑定至少定义：

- 内容控件 `Tag` 和中文 `Alias`；
- 项目字段键；
- 控件类型；
- 数据方向；
- 是否必填；
- 格式化器和校验器；
- 同步策略。

数据方向包括：

- `project_to_document`：仅从项目数据回填；
- `document_to_candidate`：文档编辑只产生候选；
- `bidirectional_candidate`：允许双向提出候选，但仍需经过批准策略；
- `computed`：只由计算服务生成。

复杂表格和列表必须使用结构化数组或明细数据，不能用不稳定的长字符串拼接冒充结构化数据。

## 16. 保存点同步

不采用逐字实时同步。同步触发点为：

- 用户点击“保存并同步”；
- 用户关闭编辑器并形成保存版本；
- ONLYOFFICE 回调形成可处理的自动保存版本。

### 16.1 保存流程

1. ONLYOFFICE 向 StaffDeck 回调保存状态。
2. StaffDeck 校验 JWT、文档键、项目归属、回调来源和参数。
3. 将编辑后文件下载到隔离临时位置。
4. 验证类型、大小、哈希和可解析性。
5. 幂等创建不可变文档版本。
6. 提取内容控件值并与打开时快照、当前批准值比较。
7. 运行字段校验和适用规则。
8. 差异进入自动、确认或仅建议路径。
9. 写入同步任务、候选和审计事件。

### 16.2 同步策略

- 自动同步：低风险、格式确定、已授权的原子字段。
- 确认同步：审核范围、日期、场所、人员等重要字段。
- 仅建议：叙述性段落、审核发现、结论和语义性内容。

### 16.3 向其他文档传播

1. 基于已批准项目值生成逐字段同步预览。
2. 展示旧值、新值、来源、目标位置和影响范围。
3. 用户确认后创建目标文档新草稿版本。
4. 按内容控件 `Tag` 更新全部匹配位置。
5. 验证文档可重新打开、控件数量和格式。
6. 保存同步记录及前后哈希。

重复回调和任务重试必须幂等，不能生成重复版本。

## 17. 材料全文与证据覆盖

本系统不承诺模型在语义上“使用每一个字”，而承诺所有上传材料都经过可验证的全文处理，并进入覆盖检查。

### 17.1 全文摄取

每份材料保存：

- 原件和 SHA-256；
- 解析全文；
- 页码、段落、表格及版面定位；
- OCR 状态、失败页和人工确认状态；
- 分块结果和覆盖率。

### 17.2 材料覆盖账本

项目页面显示：

- 完整解析；
- 部分解析；
- OCR 待确认；
- 解析失败；
- 未进入证据处理；
- 已完成信息域覆盖。

存在解析失败、失败页或未确认关键材料时，默认禁止报告定稿。

### 17.3 信息域取证

全文证据按组织信息、审核范围、能源评审、目标指标、运行控制、监视测量、审核发现等信息域组织。所有摘要和结构化值都保留原文位置，不把摘要当成原文替代品。

### 17.4 分章节生成

报告按章节生成。每个章节只装载：

- 当前项目批准数据；
- 当前节点适用规则；
- 对应材料证据；
- 对应知识库证据；
- 前序章节的受控摘要和关键结论。

完成后执行跨章节一致性检查，避免依赖一次超长上下文请求。

## 18. AI 编排边界

AI 可以：

- 提取字段候选；
- 比较多来源差异；
- 检索并引用知识依据；
- 生成章节草稿和修订建议；
- 标记缺失、冲突和证据不足；
- 对语义规则给出建议判断。

AI 不得：

- 直接批准关键字段；
- 静默修改冻结或归档文档；
- 在没有证据时补全企业事实、人员、日期、数字或条款；
- 把模型判断伪装成确定性规则结果；
- 越权读取其他项目或租户的数据；
- 绕过材料覆盖和定稿门禁。

运行时上下文分为四层：项目数据、当前规则、项目材料证据、知识库检索证据。规则应作为独立上下文字段接入任务请求编译和 Harness 执行，不并入通用 `CapabilityManifest` 的知识清单。

## 23. ONLYOFFICE 安全边界

StaffDeck 后端负责：

1. 校验用户、项目和文档权限。
2. 生成不可预测且随版本变化的文档键。
3. 使用 JWT 签名编辑配置和回调。
4. 提供短期有效的文档下载地址。
5. 校验回调签名、来源、文档键和项目归属。
6. 限制回调下载 URL，防止 SSRF。
7. 校验文件大小、类型、哈希和可解析性。
8. 把保存文件写为不可变版本，而不是覆盖原文件。

上线前必须测试伪造 JWT、过期令牌、回调重放、恶意文件、压缩炸弹、越权项目访问和网络中断恢复。

### 23.1 集成能力路线

低风险基线采用“保存回调＋后端解析 DOCX 内容控件＋显式保存并同步”，不依赖逐字实时的外部 Automation API。可先用满足许可要求的 ONLYOFFICE 版本验证业务闭环；若真实模板、并发规模、闭源分发或深度编辑器交互无法满足，再形成 Community Edition 与商业版本的对比报告，由业务、技术和法务共同决定。不得为了假设中的实时能力提前绑定商业接口。

## 24. 错误处理原则

错误必须分类并向用户提供可操作信息：

- 材料解析失败：指出文件、页码、解析器阶段及是否可 OCR 重试。
- 规则不可判定：说明缺失输入或证据，不等同于规则不通过。
- 字段冲突：展示所有候选、来源和当前批准值。
- 文档同步失败：保留原版本，允许基于同一幂等任务重试。
- ONLYOFFICE 保存失败：不把编辑会话状态伪装成已保存版本。
- 权限错误：不泄露其他租户或项目是否存在。
- 模型失败：不自动把空输出写入项目数据或正式文档。

未知错误保留请求 ID、任务 ID 和可诊断日志，前端不直接展示无上下文的底层异常。

## 25. 部署模式

### 25.1 推荐生产拓扑

```text
多台用户电脑浏览器
        ↓ 局域网 HTTPS
StaffDeck 中心服务
   ├── 数据库
   ├── 文件/对象存储
   ├── 后台任务执行器
   ├── 模型服务连接
   └── ONLYOFFICE Document Server
```

不采用每台电脑各自保存一套项目数据库的方式。独立本地部署之间不会自动共享数字员工、知识库、规则库、项目和文档。

### 25.2 数据库路线

- 开发、测试和单机验证阶段保持 SQLite，避免破坏现有迁移机制。
- 多人生产化阶段为 PostgreSQL 建立专项兼容工作，不把数据库切换混入前面业务阶段。
- PostgreSQL 适配必须覆盖模型、索引、事务、唯一约束、启动迁移、SQLite 专用 SQL、备份恢复和并发测试。

## 26. 兼容与迁移策略

1. 所有新模块通过功能开关启用。
2. 保留现有 `/api/audit-cases`、聊天绑定和知识检索行为。
3. 现有项目默认没有规则绑定和项目字段，不因升级自动改变报告行为。
4. 管理员可为旧项目执行显式初始化，生成规则建议和字段候选。
5. 旧材料继续保留原 ID、版本和哈希；三区分类通过新增元数据迁移，不移动或覆盖原件。
6. 旧报告版本继续引用原材料和知识版本，不回填新规则快照。
7. 数据库迁移幂等、可重复检测，失败时保持旧功能可运行。

## 27. TDD 与验证策略

每个阶段先增加失败测试，再实施最小代码，然后运行回归。

### 27.1 后端测试

- 规则版本不可变、项目锁定和显式迁移。
- 强制、警告、指导规则及例外权限。
- 字段候选状态机、来源、审批和乐观锁。
- 多来源冲突不得最后写入覆盖。
- 文档三区状态和冻结保护。
- ONLYOFFICE 配置、JWT、回调和重复回调幂等。
- 内容控件读取、写入、重复标签和未知标签。
- 材料全文分块、失败页和覆盖门禁。
- 分章节报告的证据引用和跨章节一致性。
- 跨租户、跨项目和越权访问隔离。

### 27.2 前端测试

- 规则库创建、校验、测试、发布和版本差异。
- 项目规则推荐、选择、锁定和迁移预览。
- 项目数据候选、批准、拒绝和冲突处理。
- 文档三区、同步预览、保存状态和冻结状态。
- ONLYOFFICE 加载失败、保存失败和恢复提示。
- 局部请求失败不得用空数据覆盖服务器状态。
- 角色权限和只读状态。

### 27.3 文档保真测试

使用真实认证模板验证：

- 页眉页脚、分节和页码；
- 嵌套表格、合并单元格和重复行；
- 中文字体和排版；
- 图片、印章和签名位置；
- 修订、批注和内容控件；
- ONLYOFFICE 保存后用 Microsoft Word 再次打开；
- 导出 PDF 后的版面一致性。

### 27.4 运行验收

每阶段至少验证：

- 后端定向和全量测试；
- Ruff；
- 前端 Vitest、i18n、配置检查和生产构建；
- `/api/health`；
- `/workspace/gallery`；
- Windows PowerShell 启动脚本；
- 对应页面和角色的浏览器验证。

## 28. 分阶段实施

### Phase 1：数据基础

- 新增规则库基础模型。
- 新增项目数据域、候选、来源、版本和冲突模型。
- 新增项目规则绑定和规则执行记录。
- 扩展项目事件审计。
- 保持现有 UI 和运行路径不变。

验收：通过 API 完成规则草稿、项目字段候选、批准、冲突和规则版本绑定的最小闭环。

### Phase 2：规则管理

- 实现规则库页面、规则测试台和版本发布。
- 实现项目规则推荐、手动选择和迁移预览。
- 接入确定性规则执行器。

验收：管理员可在网页管理规则；项目运行时只加载绑定版本和当前节点适用规则。

### Phase 3：项目文件库与覆盖账本

- 建立原始材料、工作文档和定稿归档三区。
- 复用 RapidDoc/OCR，增加解析状态、失败页和材料覆盖账本。
- 建立文档、模板和版本模型。

验收：原件不可覆盖；工作文档可版本化；解析失败材料阻止定稿。

### Phase 4：ONLYOFFICE 工作台

- 部署和接入独立 Document Server。
- 实现编辑配置、JWT、保存回调和不可变版本。
- 实现内容控件绑定、保存点同步、同步预览和冲突中心。

验收：真实模板可打开、编辑、保存和重开；重复回调不产生重复版本；冻结文档不被修改。

### Phase 5：智能报告

- 接入信息域取证和规则上下文。
- 实现分章节生成、知识引用和材料引用。
- 实现跨章节一致性检查和定稿门禁。

验收：报告可追溯到材料、知识和规则版本；未处理材料不能被伪装为已覆盖。

### Phase 6：多人生产化

- PostgreSQL 专项适配和迁移演练。
- 局域网 HTTPS、存储、备份恢复和运行监控。
- 并发编辑、容量、故障恢复和安全测试。
- 完成 ONLYOFFICE 许可与部署决策。

验收：多台客户端使用同一中心数据，权限、版本、备份和恢复达到书面验收指标。

## 29. 总体验收标准

完成全部阶段必须同时满足：

1. 知识库与规则库在数据、页面和运行时完全分离。
2. 管理员可按流程和信息域维护、测试及发布规则。
3. 项目锁定明确规则版本，升级必须人工确认。
4. 强制规则只有指定复核人可以例外放行。
5. 所有项目共享字段可追溯到来源、版本和批准记录。
6. 多文档冲突不会被最后保存自动覆盖。
7. 原始材料、工作文档和定稿文件生命周期隔离。
8. ONLYOFFICE 保存形成不可变版本并可可靠恢复。
9. 保存点同步可预览、可审计、可重试且不会修改冻结文档。
10. 所有材料均进入全文解析和覆盖账本，失败状态清晰可见。
11. 报告按章节生成并保存材料、知识和规则引用。
12. AI 不能直接批准权威数据或绕过门禁。
13. 现有普通聊天、知识问答和旧认证项目继续工作。
14. 自动化测试、文档保真测试、安全测试及运行验收全部通过。

## 30. 主要风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| AI 错误抽取传播到多份文档 | 高 | 候选区、来源、批准、同步预览和版本回退 |
| 多人修改同一字段 | 高 | 乐观锁、冲突中心、禁止最后写入覆盖 |
| 正式文档被自动改写 | 高 | 文档三区、冻结保护和新修订机制 |
| 复杂 DOCX 往返后格式损坏 | 高 | 小范围真实模板试点和文档保真回归 |
| 扫描件解析不完整却继续生成 | 高 | 失败页、覆盖账本和定稿门禁 |
| 规则变更导致历史项目不可复现 | 高 | 项目锁定规则版本、显式迁移和快照 |
| 语义判断被当成确定性规则 | 高 | 模型辅助结果必须人工确认 |
| ONLYOFFICE 回调被伪造或重放 | 高 | JWT、来源校验、幂等和短期 URL |
| SQLite 在多人写入下出现瓶颈 | 中高 | 先测量并发，再专项适配 PostgreSQL |
| ONLYOFFICE 许可或版本能力不匹配 | 高 | 在 Phase 4 前完成技术和许可验证 |
| 一次改造范围过大 | 高 | 功能开关、增量迁移、逐阶段 TDD 与验收 |

## 31. 设计结论

本项目采用“项目数据域中枢”方案：知识库提供可引用依据，规则库提供结构化执行控制，原始材料提供项目证据，ONLYOFFICE 提供人工文档编辑，AI 只提供候选与建议。所有跨文档传播均经过批准、预览、版本和审计；任何冻结文件、强制规则或材料覆盖门禁都不能被模型静默绕过。

后续实施计划必须以本规格为约束，并从 Phase 1 开始采用 TDD 逐项落地。
