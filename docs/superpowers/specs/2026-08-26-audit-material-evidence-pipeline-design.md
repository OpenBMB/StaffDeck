# 审核项目材料复用与全文证据流水线设计

**日期：** 2026-08-26

**状态：** 待用户审阅

**适用范围：** StaffDeck Harness v2、审核报告生成 SOP、知识库检索、模型配置

## 1. 背景与问题

当前审核报告生成流程能把 PDF、DOCX 等附件提取为完整文本文件，也能把知识库文档的原始全文保存并切分为知识块。但“文件已保存”不等于“本次报告生成已经覆盖全文”。现有流程存在以下可验证问题：

1. `read_file` 的工具结果按 12,000 字符整体截断，长文本正文可能截断后面的 `continuation_token`，导致续读失败或重复读取同一段。
2. Harness 模型上下文仅完整保留近期工具结果，较早的正文被压缩为回执；最终写作模型无法直接看到所有已读取片段。
3. 模型请求在应用层被限制为约 32,000 tokens。接近 40,000 个中文字符的单份审核记录，加上其他材料、SOP 和知识证据后会触发裁剪。
4. 知识库检索默认返回有限的 Top-K 知识块；每个 TaskFrame 最多两次成功检索。该机制适合问答，但不足以证明审核报告逐要素覆盖了所需知识。
5. 当前审核报告 SOP 把 `audit_materials` 作为普通文本槽位。槽位没有持久保存附件 ID、哈希、提取路径、处理状态和版本。
6. Harness 只把当前请求的 `request.attachments` 复制到当前 TaskFrame。任务完成、新建任务或新建对话后，已有材料无法按审核项目重新装载，因此数字员工可能再次要求上传。
7. 当前 SOP 的知识库范围和强制知识库引用为空，“通读全部材料”和“调用审核报告撰写技能”只是自然语言指令，不是可执行完成条件。

## 2. 目标

本设计实现以下业务目标：

1. 同一审核项目中的同一份材料只需上传一次；同一会话、新对话和恢复任务都能按项目重新使用。
2. 材料只在同一租户、同一授权审核项目内复用，不跨企业或跨项目自动共享。
3. 保证每份材料全文已提取、每个文本块已进入处理台账，并能发现遗漏、失败和版本变化。
4. 按审核要素检索知识库，记录查询、命中、引用和无结果状态。
5. 分章节生成报告，避免依赖一次超长上下文请求。
6. 最终报告中的事实和结论能够回溯到项目材料或知识库来源。
7. 现有普通聊天、普通知识问答和非审核类 SOP 不受影响。

## 3. 非目标

1. 不承诺模型在语义上“使用了每一个字”。系统承诺的是每个文本块均已处理并进入可追踪的证据流水线。
2. 不自动把项目材料写入企业长期知识库。
3. 不在不同企业或不同审核项目之间复用案例证据。
4. 不以单纯扩大模型上下文作为全文覆盖方案。
5. 第一轮不引入新的外部向量数据库；知识检索增强通过稳定接口分阶段实现。

## 4. 核心术语

- **审核项目（Audit Case）：** 一次明确的初审、监督或再认证任务，是材料、证据、知识版本和报告版本的隔离边界。
- **项目材料（Case Material）：** 本次审核上传的审核计划、审核记录、组织信息表、绩效确认表、不符合报告、改进建议和报告模板等。
- **稳定知识（Reference Knowledge）：** 标准、认证规则、企业制度、审核准则和长期有效的编写规则，继续存放在 StaffDeck 知识库。
- **材料清单（Material Manifest）：** 项目材料的结构化状态列表。
- **证据台账（Evidence Ledger）：** 文本块、审核要素、知识依据和报告章节之间的映射记录。
- **覆盖检查（Coverage Gate）：** 报告生成前必须通过的机器可验证条件。

## 5. 方案选择

### 5.1 仅修改技能和 SOP

可以减少同一活动任务内的重复追问，但附件仍属于当前请求和 TaskFrame，任务结束后槽位会清空。该方案不能解决跨对话复用和全文覆盖验证，不单独采用。

### 5.2 每个审核项目建立私有知识库

可以复用现有知识入库和检索能力，但会把一次性案例证据与长期知识混合，增加版本、权限、删除和检索污染风险。不作为主方案，可用于临时迁移。

### 5.3 审核项目材料库与证据台账

新增独立的审核项目边界，保留原有知识库作为稳定知识来源。项目材料确定性处理，知识库按要素检索，报告按章节生成。该方案职责清晰、可验证、适合后续扩展，作为最终方案。

## 6. 总体架构

数据流如下：

```text
用户上传材料
  -> 创建或选择审核项目
  -> 原文件持久化并计算 SHA256
  -> 文本提取与完整性检查
  -> 确定性分块并登记全部块
  -> 逐块提取事实和审核证据
  -> 按审核要素建立材料证据矩阵
  -> 按审核要素检索指定知识库版本
  -> 合并项目证据与知识依据
  -> 分章节生成报告草稿
  -> 覆盖、一致性和引用检查
  -> 确定性合并并发布报告文件
```

模型负责分类、证据抽取、相关性判断和写作；后端负责材料生命周期、分块完整性、状态机、覆盖统计、来源引用和报告文件组装。

## 7. 数据模型

### 7.1 `audit_cases`

字段至少包括：

- `id`
- `tenant_id`
- `owner_user_id`
- `organization_name`
- `report_type`
- `management_systems_json`
- `status`: `collecting | processing | ready | generating | review | completed | archived`
- `knowledge_base_version_ids_json`
- `active_report_version_id`
- `created_at`
- `updated_at`

同一企业可以有多个审核项目，系统不得仅凭企业名称自动合并项目。

### 7.2 `audit_case_materials`

字段至少包括：

- `id`
- `audit_case_id`
- `attachment_id`
- `material_type`
- `filename`
- `content_type`
- `sha256`
- `size`
- `storage_key`
- `extracted_text_storage_key`
- `characters`
- `extraction_status`: `pending | succeeded | failed | unsupported`
- `processing_status`: `pending | processing | succeeded | failed`
- `version`
- `supersedes_material_id`
- `created_at`
- `updated_at`

同一项目内相同 SHA256 的文件幂等复用。相同文件名但不同 SHA256 视为新版本，保留旧版本并要求用户确认是否作为当前版本。

### 7.3 `audit_case_material_chunks`

字段至少包括：

- `id`
- `material_id`
- `chunk_index`
- `start_char`
- `end_char`
- `content_sha256`
- `content`
- `page_refs_json`
- `processing_status`
- `extracted_facts_json`
- `created_at`
- `updated_at`

分块必须覆盖从 0 到全文长度的连续字符区间，禁止出现未登记空洞。标题、表格边界和段落边界优先；目标大小 900 至 1,200 字符。超长段落按字符范围确定性切分。

### 7.4 `audit_evidence_ledger`

字段至少包括：

- `id`
- `audit_case_id`
- `audit_element_id`
- `source_kind`: `case_material | knowledge`
- `source_id`
- `source_version_id`
- `chunk_id`
- `source_ref`
- `evidence_type`: `conformity | improvement | nonconformity | context | rule`
- `evidence_text`
- `confidence`
- `report_section_ids_json`
- `created_at`

### 7.5 `audit_report_versions`

保存报告版本、章节草稿、最终文件、所用材料版本、知识库版本、覆盖快照和审核组长确认状态。

## 8. 材料存储与复用

1. 原文件进入项目级受控存储，不把宿主机路径暴露给模型。
2. TaskFrame 需要材料时，由后端把当前版本复制到隔离工作区，并生成结构化描述符。
3. 新对话中用户选择审核项目后，系统从数据库重新装载材料清单，不依赖聊天历史恢复附件。
4. 默认只允许项目所有者、同租户授权团队成员和管理员访问。
5. 项目归档后材料保持只读；删除项目时按租户数据保留策略清理原文件、提取文本和派生块。

## 9. 全文处理与覆盖定义

系统提供三类覆盖指标：

### 9.1 文件覆盖率

```text
成功提取且已完成分块的当前材料数 / 当前材料总数
```

生成报告前必须为 100%。失败、空文本和不支持格式必须列为材料缺口，不能静默跳过。

### 9.2 文本块覆盖率

```text
processing_status=succeeded 的块数 / 已登记块总数
```

生成报告前必须为 100%。所有块的字符区间联合必须等于提取全文区间。

### 9.3 审核要素覆盖率

每个必需要素必须处于以下状态之一：

- 已找到项目材料证据；
- 已找到知识依据；
- 已记录明确的“证据不足”；
- 经审核组长确认不适用。

不存在状态的要素阻止最终报告发布。

## 10. 知识库检索

### 10.1 检索边界

审核项目固定所用知识库版本。报告生成期间知识库更新不改变当前项目结果；用户明确升级版本后重新计算受影响要素。

### 10.2 检索方式

审核流程不再让模型自行决定是否调用最多两次 `knowledge_search`。新增后端编排能力 `audit_evidence_search`：

1. 根据适用体系加载必需要素清单。
2. 为每个要素生成受控查询。
3. 调用现有 `KnowledgeService` 获取候选文档、分桶和知识块。
4. 对候选结果去重、扩展相邻块并写入证据台账。
5. 对零命中、低置信度和冲突结果记录状态。

一期继续使用现有词法排名和 LLM 路由。后续 BM25、向量检索和 reranker 通过统一检索接口接入，不改变审核项目或证据台账的数据结构。

### 10.3 召回目标

“覆盖所有能检索到的内容”不可作为可验证条件，因为检索结果随查询和排序变化。替代条件为：每个审核要素都执行预定义查询组，记录候选数、最终采用证据、被排除原因和零命中状态，并用固定测试集监控召回率。

## 11. 模型上下文与生成策略

1. 不把整个项目材料和全部知识块一次性发送给模型。
2. 每个文本块单独或小批量完成事实与证据抽取，结果立即持久化。
3. 每个报告章节只加载该章节对应的要素、项目证据、知识依据和格式规则。
4. 章节草稿保存为结构化状态或工作区文件，最终报告由后端按模板顺序合并。
5. 最终一致性检查读取章节摘要、证据引用和覆盖台账；发现问题时只重生成受影响章节。
6. 模型输入预算保持应用层可控，不把正确性依赖于某个模型的超长上下文。

模型配置增加经过验证的 `context_window_tokens` 和 `safe_input_tokens` 元数据。StaffDeck 只在提供方验证成功后提高输入预算，并预留系统提示、工具结果和输出空间。默认 32,000-token 安全预算继续适用于未知模型。

当前配置的模型 ID 应从兼容别名 `deepseek-chat` 迁移为提供方明确支持的 `deepseek-v4-flash` 或其他已验证模型 ID。模型切换可以改善路由和写作质量，但不得绕过覆盖检查。

## 12. SOP 与技能调整

审核报告 SOP 发布新版本，保留旧版本供进行中的任务完成。新版本的核心槽位为：

- `audit_case_id`
- `report_type`
- `management_systems`
- `organization_name`
- `material_manifest_status`
- `evidence_coverage_status`
- `knowledge_coverage_status`

节点调整为：

1. `select_or_create_audit_case`
2. `collect_materials`
3. `ingest_and_validate_materials`
4. `build_material_evidence_ledger`
5. `retrieve_reference_knowledge`
6. `trim_template`
7. `generate_report_sections`
8. `consistency_and_coverage_check`
9. `output_and_confirm`
10. `handoff_lead_auditor`

`collect_materials` 必须先调用项目材料清单能力；只询问缺失、提取失败、版本冲突或用户要求替换的文件。仅凭 `audit_materials` 文本描述不得把材料判定为齐全。

SOP 必须声明审核报告技能、项目材料能力和指定知识库为强制能力。完成条件由后端结构化状态决定，不由模型自由表述决定。

新增 API：

- `POST /api/audit-cases`
- `GET /api/audit-cases`
- `GET /api/audit-cases/{case_id}`
- `POST /api/audit-cases/{case_id}/materials`
- `GET /api/audit-cases/{case_id}/materials`
- `POST /api/audit-cases/{case_id}/process`
- `GET /api/audit-cases/{case_id}/coverage`
- `POST /api/audit-cases/{case_id}/reports`
- `GET /api/audit-cases/{case_id}/reports/{version_id}`

数字员工对话页增加审核项目选择器和材料状态卡，显示：

- 已上传和缺失材料；
- 文件版本与哈希状态；
- 文本提取状态；
- 文本块处理进度；
- 审核要素覆盖率；
- 知识检索覆盖率；
- 当前报告版本。

新建对话时选择已有审核项目后，不再要求重新上传已验证材料。

## 14. 错误处理

1. 文档提取失败：材料状态置为 `failed`，保留原文件和错误码，只询问该文件的替代版本。
2. 分页 token 无效：后端不得让模型猜测；使用服务器保存的读取游标或从最近成功偏移恢复。
3. 文件版本冲突：保留两个版本，暂停生成并请求用户选择当前版本。
4. 知识检索零命中：写入要素覆盖状态，不虚构知识依据。
5. 模型调用失败：已完成块保持幂等状态，仅重试未完成批次。
6. 报告生成中断：从未完成章节恢复，不重新上传材料、不重复处理已成功块。
7. 证据矛盾：标记冲突来源并转审核组长确认。

## 15. 安全与权限

1. 所有项目、材料、块、证据和报告查询必须包含 `tenant_id`。
2. 默认只允许项目所有者和明确授权成员访问。
3. 工具结果不得向模型暴露宿主机绝对路径、密钥或跨项目存储键。
4. 证据引用使用受控 ID 和沙箱路径。
5. 审计日志记录材料新增、替换、处理、知识版本变更、报告生成和人工确认。

## 16. 可观测性

每次运行至少记录：

- 审核项目 ID 和报告版本；
- 当前材料数、成功提取数和失败数；
- 总块数、已处理块数和失败块数；
- 每个要素的材料证据数、知识证据数和缺口状态；
- 每次知识检索的候选数、采用数和查询耗时；
- 每个章节的模型 ID、输入 tokens、输出 tokens、引用数量和重试次数；
- 覆盖检查失败原因。

禁止在普通日志中记录完整材料正文或 API Key。

## 17. 测试策略

### 17.1 单元测试

- 长 `read_file` 结果裁剪后仍完整保留分页 token 和元数据。
- 确定性分块无重叠空洞并覆盖全文。
- 相同 SHA256 幂等复用，不同 SHA256 产生新版本。
- 覆盖率计算准确，失败材料和失败块阻止发布。
- SOP 已满足材料清单时不再生成上传问题。

### 17.2 集成测试

- 上传一份超过 40,000 字的审核记录并处理至所有块成功。
- 同一会话下一轮继续时不要求重传。
- 新对话选择同一审核项目后不要求重传。
- 不同审核项目不能访问对方材料。
- 指定知识库版本后按每个审核要素生成证据台账。
- 模型上下文超过安全预算时仍能通过分章节流程完成报告。
- 中断后恢复只处理未完成块和章节。

### 17.3 端到端验收

使用一套包含审核计划、组织信息表、约 40,000 字审核记录、绩效确认表、改进建议和报告模板的固定样本：

1. 所有当前材料文件覆盖率为 100%。
2. 文本块覆盖率为 100%。
3. 必需要素状态覆盖率为 100%。
4. 新对话复用项目后上传提示次数为 0。
5. 报告中抽样事实能回溯到正确材料块或知识块。
6. 删除任一必需材料后覆盖检查失败并给出准确缺口。

## 18. 分阶段交付

### 阶段一：稳定现有 Harness

- 修复 `read_file` 结果裁剪与分页 token。
- 在同一 TaskFrame 中持久合并已有附件描述符。
- 增加结构化材料清单槽位和同任务不重复追问测试。

该阶段独立可发布，降低当前失败率，但不宣称已经支持跨对话复用。

### 阶段二：审核项目材料库

- 增加审核项目、材料版本、项目权限和材料状态 API。
- 支持新对话选择项目并重新装载材料。
- 更新审核报告 SOP 为项目驱动。

### 阶段三：全文证据台账与分章节生成

- 增加全文分块、证据抽取、覆盖检查和章节草稿。
- 报告发布必须通过覆盖 Gate。
- 增加固定样本端到端测试。

### 阶段四：知识检索增强与模型预算

- 引入审核要素驱动的批量知识检索编排。
- 在统一接口后增加 BM25、向量召回和 reranker。
- 根据已验证模型上下文配置安全输入预算。

## 19. 迁移与兼容

1. 数据库迁移只新增表和可空引用，不破坏现有会话和知识库记录。
2. 现有审核 SOP 保留原版本；新任务使用新版本，进行中任务继续使用已固定版本。
3. 已上传但未归属项目的历史附件不自动迁移，避免跨项目错误关联。
4. 普通知识检索继续保留两次调用预算；审核编排通过新的受控能力运行，不改变普通聊天成本。
5. 新功能按租户功能开关灰度启用，先在本地 `tenant_demo` 使用固定样本验证。

## 20. 验收结论

只有同时满足以下条件，系统才可以向用户声明“本次审核报告已基于全部项目材料和规定知识范围生成”：

1. 当前材料文件覆盖率为 100%。
2. 当前材料文本块覆盖率为 100%。
3. 必需要素状态覆盖率为 100%。
4. 所有引用都指向有效材料版本或知识库版本。
5. 最终报告使用的材料、知识和覆盖快照已写入报告版本记录。
6. 审核组长完成最终确认，或报告明确标记为待确认草稿。
