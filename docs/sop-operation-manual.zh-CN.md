# StaffDeck SOP 与外展超细粒度操作手册

使用本手册，你可以为数字员工创建一套可路由、可执行、可追踪、可回滚的 SOP，并将其用于网页对话、微信、企业微信、飞书、钉钉和定时任务。

| 文档信息 | 说明 |
|---|---|
| 适用版本 | 当前仓库中的 StaffDeck 企业控制台与 Harness v2 运行时 |
| 适用角色 | SOP 设计人员、运营人员、数字员工负责人、实施人员、管理员、排障人员 |
| 核验日期 | 2026-08-14 |
| 预计上手时间 | 创建并测试第一个 SOP 约 15 至 30 分钟，不含外部工具配置 |

> [!TIP]
> 如果你第一次使用 StaffDeck，先完成“第 1 章：SOP 快速上手”，再阅读按钮和模型决策参考。不要从字段字典开始逐项配置。

> [!IMPORTANT]
> 当前企业编辑器新建 SOP 时会以 `published` 状态保存。第一次点击保存可能直接启用该 SOP，不是仅保存草稿。请先在测试员工中完成验证。

## 1. SOP 快速上手

SOP 是一份结构化业务流程，不是单段提示词。它包括触发意图、流程目标、节点、连线、必需信息、回复规则，以及每一步可用或必须使用的工具、技能和知识库。

> [!NOTE]
> 数据库和部分接口沿用 `Skill` 命名，产品界面和 Harness v2 运行时将其作为 SOP 使用。本文中的 SOP 与这些接口中的 Skill 指同一类资源。

### 步骤 1：选择目标数字员工

1. 登录 StaffDeck 企业控制台。
2. 在全局员工选择器中选择要配置的数字员工。
3. 确认选择的不是“整体员工”或开放广场范围。
4. 从左侧导航进入 **SOP**。

> **截图占位 01｜选择目标数字员工并进入 SOP**  
> 页面：`http://127.0.0.1:5173/enterprise/skills`  
> 范围：左侧导航、员工选择器和页面标题。  
> 标注：① 当前员工；② SOP 导航入口；③ 当前页面标题。

> [!WARNING]
> 员工范围决定 SOP 保存到哪个本地分支。选错员工不会只是“显示错了”，可能把流程配置给错误的数字员工。

### 步骤 2：新建 SOP

1. 点击右上角 **新增**。
2. 选择 **新建空白 SOP**。
3. 进入 SOP 工作台后，在左侧输入要整理的流程说明。

> **截图占位 02｜新建 SOP 入口**  
> 页面：`http://127.0.0.1:5173/enterprise/skills`  
> 范围：页面右上角“新增”菜单。  
> 标注：① 新增；② 新建空白 SOP；③ 从广场复制；④ 从数字员工复制。

如果已有可复用流程，也可以选择：

- **从广场复制**：复制组织共享的 SOP；
- **从数字员工复制**：复制另一个可见员工的 SOP。

若要修改已有 SOP，请在该 SOP 行尾的操作菜单中选择 **编辑本地版本**。它会在当前员工分支上修改，不直接修改其他员工副本。

> **截图占位 02A｜从开放广场选择 SOP**  
> 页面：`http://127.0.0.1:5173/enterprise/platform`  
> 范围：开放广场中的 SOP 资源区和资源卡片。  
> 标注：① SOP 广场；② 资源名称；③ 业务描述；④ 复制到 SOP。

### 步骤 3：用自然语言生成流程草稿

在输入框中写清业务目标、触发范围、必须收集的信息、执行步骤、禁止事项和必需能力，然后点击 **发送/生成**。

```text
业务目标：处理企业客户退款申请。
触发范围：用户明确提出退款、退货或取消已支付订单。
必须收集：订单号、申请原因、商品状态、联系方式。
执行步骤：确认身份 -> 查询订单 -> 校验政策 -> 用户确认 -> 提交退款 -> 告知结果。
禁止事项：未查询订单前不得承诺退款；高风险或工具失败时转人工。
必需能力：订单查询工具、退款申请工具、售后政策知识库。
输出要求：每轮只追问仍缺失的必要信息；工具返回后如实反馈。
```

> **截图占位 03｜输入流程说明并生成草稿**  
> 页面：`http://127.0.0.1:5173/enterprise/skills/distill?mode=create`  
> 范围：左侧生成对话区。  
> 标注：① 流程说明输入框；② 附件；③ 模型选择；④ 发送按钮。

> [!TIP]
> 不要只写“做一个退款 SOP”。输入越短，越多业务边界会被交给生成模型自行推断。

### 步骤 4：检查触发、目标和回复规则

草稿生成后，先检查以下内容，再处理节点细节：

1. **触发意图**是否明确说明用户想完成的业务动作；
2. **用户说法示例**是否包含常用口语和同义表达；
3. **目标**是否可以验证，而不是“提升体验”一类口号；
4. **必需信息**是否只包含真正阻塞办理的字段；
5. **回复规则**是否限制错误承诺、敏感信息和输出格式。

> **截图占位 04｜检查 SOP 全局字段**  
> 页面：`http://127.0.0.1:5173/enterprise/skills/distill?...`  
> 范围：源码视图中的基本信息、触发意图、目标和回复规则。  
> 标注：① 触发意图；② 用户说法；③ 目标；④ 必需信息；⑤ 回复规则。

### 步骤 5：检查节点和连线

切换到 **流程图** 视图，按业务顺序检查：

1. 起始节点是否正确；
2. 每个节点是否只有清晰、单一的目标；
3. 节点指令是否包含输入、动作、成功条件和失败处理；
4. 写操作前是否存在用户确认节点；
5. 连线方向和条件是否可达；
6. 工具失败、结果未知和高风险场景是否进入安全路径；
7. 需要人工处理时，是否使用 handoff 节点，或显式允许 `handoff_human`。

> **截图占位 05｜检查流程图节点和连线**  
> 页面：`http://127.0.0.1:5173/enterprise/skills/distill?...`  
> 范围：完整流程图和右侧节点属性面板。  
> 标注：① 起始节点；② 当前节点；③ 连线条件；④ 新增节点；⑤ 节点属性。

> [!IMPORTANT]
> 节点位置和画布缩放只影响显示；新增、删除节点，修改连线或条件会改变真实执行状态机。

### 步骤 6：绑定工具、技能和知识库

在每个节点中配置该步骤可以使用的能力：

- **可选引用**：模型按当前任务需要决定是否调用；
- **必需引用**：能力必须成功执行，当前 TaskFrame 才能完成；
- **仅限 SOP**：只有被当前节点明确引用时，能力才会出现在可调用清单中；
- **通用**：普通对话和 SOP 中均可能被模型自主调用。

> **截图占位 06｜配置节点能力引用**  
> 页面：`http://127.0.0.1:5173/enterprise/skills/distill?...`  
> 范围：节点属性面板中的工具、技能和知识库引用。  
> 标注：① 工具；② 通用技能；③ 知识库；④ 必需/可选状态。

> **截图占位 07｜设置能力范围**  
> 页面：工具、技能或知识库编辑页。  
> 范围：“能力范围”控制项。  
> 标注：① 通用；② 切换开关；③ 仅限 SOP；④ 说明文字。

> [!WARNING]
> 高风险写操作工具优先设为“仅限 SOP”，并且只在用户确认后的执行节点中引用。设为“仅限 SOP”但没有节点引用时，运行模型看不到该能力。

### 步骤 7：保存前审阅差异

1. 点击 **保存 SOP 版本**。
2. 检查 SOP 名称、业务域和新版本号。
3. 阅读差异，确认没有意外删除节点或能力引用。
4. 返回编辑器源码视图确认 SOP ID，并再次检查全局员工选择器。
5. 重新打开保存审阅后点击 **保存**。

> **截图占位 08｜保存 SOP 版本**  
> 页面：`http://127.0.0.1:5173/enterprise/skills/distill?...`  
> 范围：保存审阅弹窗。  
> 标注：① 名称；② 业务域；③ 版本；④ 差异；⑤ 保存。

> [!IMPORTANT]
> 新建 SOP 会以 `published` 状态保存并直接启用；编辑既有 SOP 时保留原状态。生产 SOP 建议先在测试员工中创建和验证，再复制或发布到目标范围。

### 步骤 8：通过聊天验证

至少完成两类测试：

1. **定向测试**：在聊天中使用 `/sop <skill>`，验证流程本身；
2. **自然语言测试**：直接发送用户真实说法，验证 Planner 能否正确选择 SOP。

定向测试通过不代表自然语言路由一定正确。

> **截图占位 09｜通过聊天定向测试 SOP**  
> 页面：StaffDeck 聊天工作区。

### 步骤 9：检查 Trace 和回归结果

重点确认：

- Planner 选择的 SOP 是否正确；
- 当前节点和缺失槽位是否正确；
- 必需能力是否实际成功执行；
- `sop_specific` 能力是否只在指定节点出现；
- 下一节点是否来自允许连线；
- 工具参数、工具结果和最终回复是否一致。

> **截图占位 10｜检查 SOP 执行 Trace**  
> 页面：对应会话或反馈/日志页面。  
> 范围：Planner 决策、TaskFrame、能力调用和最终回复。  
> 标注：① SOP ID；② 当前节点；③ 必需能力；④ 调用结果；⑤ 下一节点。

### 完成标准

完成以下检查后，才可以认为 SOP 已具备上线条件：

- 典型说法能触发，边界说法不会误触发；
- 已知信息不会重复追问；
- 缺失信息只追问必要字段；
- 必需工具真实调用且失败时不伪造成功；
- 写操作前有明确确认或外部审批；
- 结果未知时不会自动重复外部写操作；
- 转人工和回滚路径已验证。

### 按钮影响标记

后续章节使用以下标记说明每个按钮是否影响模型：

| 标记 | 含义 | 典型例子 |
|---|---|---|
| **D：直接影响** | 内容进入模型输入，或改变模型任务目标 | 触发意图、节点指令、定时任务说明 |
| **I：间接影响** | 改变可选 SOP、员工、能力或执行拓扑 | 启用 SOP、删除节点、能力范围 |
| **E：只影响执行** | 改变运行时间、投递或暂停状态 | 立即执行、暂停任务、渠道凭证 |
| **U：纯界面/查看** | 只改变显示、筛选、缩放或导航 | 搜索、分页、流程图缩放 |

一个控件可以同时属于多个等级。“智能分发”会调用独立路由模型选择员工，因此会改变员工及其 SOP/能力集合；当前没有员工专属模型绑定，所有员工运行任务统一使用租户中已启用的默认模型。

## 2. 角色、员工范围与权限

### 2.1 账号角色

系统账号角色为 `admin` 和 `member`：

- 管理员可以管理租户内整体资源和可见员工；
- 普通成员通常只能管理自己拥有的数字员工及其本地资源；
- 后端权限校验是最终依据，不能把“页面按钮可见”当作已经授权。

### 2.2 页面左上或全局员工范围

操作前必须先确认当前范围：

- **整体/开放广场范围**：组织级模板和共享资源；
- **某个数字员工范围**：该员工的本地 SOP 分支和资源绑定。

同一个按钮在两个范围中的含义可能不同：

- 整体范围的“删除”会让组织 SOP 列表不再显示该流程；
- 员工范围的“移除”只隐藏该员工的本地引用，不删除广场或其他员工的副本；
- 员工范围可使用“从广场同步”和“发布到广场”；
- 定时任务必须绑定具体员工，不能配置在整体员工上。

### 2.3 上线前权限检查

1. 确认当前租户正确。
2. 确认当前选择的是目标数字员工，而不是整体员工。
3. 确认操作者是该员工负责人或管理员。
4. 确认目标工具、技能、知识库对该员工可见且处于可用状态。
5. 确认渠道由当前操作者创建，或当前操作者是管理员。

## 3. 模型如何使用 SOP

模型不会把 SOP 当作一篇背景资料自由参考。Harness v2 会先选择当前任务适用的 SOP，再由服务端把当前节点编译成受约束的任务，最后让隔离的 Task Agent 在授权能力范围内执行。

> [!NOTE]
> SOP 只有在当前员工可见且已启用时，才会进入 Planner 的候选列表。草稿、已停用或已从员工移除的 SOP 不应参与新任务路由。

> [!IMPORTANT]
> SOP 可以约束模型的任务边界、必填信息、已编译的必需能力和允许迁移，但不能赋予模型原本没有的工具权限，也不能让模型跳到未连接节点。一般完成条件和连线业务条件仍由模型结合执行结果判断，除非业务系统另有确定性校验。

> [!WARNING]
> 节点中引用了工具，不代表一定调用。可选能力由模型按需决定；成功编译进当前 `TaskRequirement` 的必需能力才构成完成门槛。高风险动作应同时使用“仅限 SOP”、必需引用、确认令牌或外部审批，以及业务侧幂等控制。

### 3.1 整体执行过程

一次消息从进入系统到产生回复，会经过以下阶段：

当用户消息、渠道消息或定时任务进入系统后，Turn Planner 会结合当前消息、精简上下文、会话状态以及当前员工已启用的 SOP，判断本轮应该继续已有流程、切换挂起任务、启动新 SOP，还是按普通会话处理。服务端随后校验 Planner 的结果，确定合法的 SOP 和当前步骤，并将本轮工作拆分、持久化为有顺序和依赖关系的 TaskFrame。对于可以执行的 TaskFrame，系统会把当前 SOP 节点、已知与缺失槽位、完成条件、允许迁移以及当前步骤的授权能力编译成隔离的 TaskRequirement，再交给 Harness Task Agent 串行调用工具、技能或知识库。每次调用都会记录真实结果并重新检查授权；Task Agent 根据执行情况返回完成、等待用户补充、转人工、失败或动作预算耗尽等结果，调度引擎也可能因前置依赖未完成而暂缓执行。最后，系统持久化槽位、步骤和任务状态，在满足当前硬约束后推进到允许的下一节点，并由 Response Generator 汇总任务结果、引用和产物，生成用户可见回复；网页会话直接返回，外部渠道会通过 outbox 投递到原会话目标，定时任务则把结果保存在对应运行记录中。

```text
用户消息 / 渠道消息 / 定时任务
              |
              v
Turn Planner：判断继续、切换、新建还是普通会话任务
              |
              v
服务端校验：SOP 必须可见、已启用，步骤由状态机确定
              |
              v
TaskFrame：把本轮工作拆成有顺序、可持久化的任务
              |
      +-------+----------------+
      |                        |
      v                        v
依赖未满足：blocked        可进入执行
持久化通常保持 queued          |
                               v
TaskRequirement：编译当前节点、槽位、完成条件和能力清单
                               |
                               v
Harness Task Agent：串行选择并调用已授权能力
                               |
          +------------+------------+------------+
          |            |            |            |
          v            v            v            v
      completed  awaiting_user  handoff/failed  action_budget
          |            |            |            |
          v            v            v            v
   推进允许的下一步  保存状态并追问  转人工或结束  未完成，通常重新 queued
                 |
                 v
Response Generator：合成用户可见回复和引用/产物
                 |
                 v
网页返回，或通过渠道 outbox 投递到原会话目标
```

> 范围：Planner、TaskFrame、TaskRequirement、Harness Agent、能力调用、状态更新和回复生成。  
> 标注：① 唯一 SOP 路由阶段；② 服务端状态机；③ 授权能力边界；④ 完成/追问/转人工分支。

这是一条**带持久化状态的循环**，不是“把完整 SOP 塞进一次提示词后让模型自由完成”。如果当前步骤需要用户补充信息，系统会保存状态并在下一轮继续；如果任务完成，才会按允许连线推进下一节点。

### 3.2 阶段一：Turn Planner 选择任务和 SOP

Turn Planner 是唯一负责 SOP 意图和任务顺序规划的模型阶段。

#### Planner 使用什么信息

- 当前用户消息；
- 精简对话上下文和相关记忆；
- 当前会话中的非终态 TaskFrame；已完成依赖的结果会在后续编译相关 `TaskRequirement` 时提供；
- 当前员工可路由的 `available_sops`。

#### Planner 做什么决定

| 场景 | Planner 行为 | 后续结果 |
|---|---|---|
| 用户在回答当前 SOP 的追问 | `continue_active` | 继续当前任务和服务端保存的当前步骤 |
| 用户明确继续一个挂起任务 | `switch_to_pending` | 切换到指定 pending TaskFrame |
| 用户提出新的 SOP 业务 | `start_new_task` | 从可用 SOP 中选择并创建任务；受依赖或动作预算限制时可保持 queued |
| 多个 SOP 无法区分 | `clarify` | 先向用户澄清，不猜测流程 |
| 普通咨询或没有匹配 SOP | `answer_only` + conversation frame | 仍经过 Harness，但不伪造 SOP |
| 顶层用户请求转人工 | `handoff_human` + conversation frame | 走独立会话转人工路径，不受某个 SOP 节点约束 |

SOP frame 执行过程中的转人工不由 Planner 的 `handoff_human` 直接驱动，而是由 Task Agent 返回 `handoff`；服务端随后检查当前节点是否为 handoff 类型，或是否在 `allowed_actions` 中声明 `handoff_human`。

#### Planner 不做什么

- 不读取 SOP 节点图；
- 不选择工具、通用技能或知识库；
- 不生成工具调用；
- 不决定新 SOP 的起始步骤；
- 不生成最终用户回复。

> [!TIP]
> 调整触发意图、说法示例、SOP 名称和描述，主要影响这一阶段。调整节点工具引用，不会让 Planner 用工具名匹配 SOP。

服务端会再次规范 Planner 输出：新任务只能选择当前 `available_sops` 中的 SOP，新 SOP 从服务端确定的起始节点开始，进行中 SOP 使用持久化的当前节点。模型不能通过输出一个任意步骤 ID 来跳步。

### 3.3 阶段二：持久化 TaskFrame

Planner 不是直接开始执行工具，而是先把本轮工作拆成一个或多个 `TaskFrame`。每个 TaskFrame 都有独立身份、顺序、依赖和状态。

| 字段 | 作用 |
|---|---|
| `kind` | 区分 SOP 任务与普通 conversation 任务 |
| `goal` / `requirements` | 保存本任务要完成的目标和用户附加要求 |
| `skill_id` / `step_id` | 关联 SOP 和服务端确定的当前步骤 |
| `depends_on_task_ids` | 指明必须先完成的前置任务 |
| `slots` | 用于保存稳定结构化信息；已知的消息复制字段会被过滤，原始用户消息另存为事实源 |
| `status` | 数据模型支持 `queued`、`running`、`awaiting_user`、`blocked`、`completed`、`handoff`、`failed` 或 `cancelled`；当前依赖等待通常仍持久化为 `queued` |

TaskFrame 被持久化后，即使一轮中需要等待用户补充信息，系统也能在后续消息中继续原任务，而不是只依赖模型“记住”上一次做到哪里。

> [!NOTE]
> 一条用户消息可以产生多个有依赖关系的 TaskFrame。例如“先查订单，再判断退款资格，并把结果整理成说明”可以被拆为有顺序的任务，但 Planner 不应擅自扩展用户没有要求的业务阶段。

### 3.4 阶段三：编译当前 TaskRequirement

服务端把一个 TaskFrame 和当前 SOP 节点编译成隔离的 `TaskRequirement`。Task Agent 看到的是这份任务合同，而不是未经筛选的完整对话历史。

| TaskRequirement 内容 | 来源 | 对执行的影响 |
|---|---|---|
| `goal`、`requirements` | Planner 和用户原始要求 | 限定模型必须完成的任务边界 |
| 当前 SOP 和节点指令 | 服务端状态机 | 规定当前步骤目标和规则 |
| `required_slots` | 节点 `expected_user_info` 减去已知槽位 | 决定还缺哪些必要信息 |
| `completion_criteria` | 当前任务与节点 | 作为模型完成判断要求，不是全部由服务端规则计算 |
| 必需能力和知识库 | 节点的 required 引用 | 成功编译进 TaskRequirement 后，未成功执行时不得 completed |
| 允许迁移 | 当前节点的出边 | 服务端限制 `next_step_id` 必须邻接；业务条件主要由模型判断 |
| 能力快照 | 当前员工、SOP、节点和能力范围 | 限定当前 HarnessRun 可发现和调用的能力 |
| 前置任务结果 | 已完成依赖 TaskFrame | 让后续任务使用真实执行结果 |

如果必填槽位已经存在，服务端会从 `required_slots` 中移除，模型不应重复追问。如果缺失信息可以通过已授权工具或知识库可靠获得，Task Agent 应先执行相关能力，再只追问仍会阻塞结论的字段。

### 3.5 阶段四：Harness Task Agent 选择能力并执行

每个 TaskFrame 由独立的小型 AgentLoop 执行。当前 HarnessRun（通常对应当前 SOP 步骤）使用冻结的能力快照，并在每次调用前复核实时授权；TaskFrame 推进到下一步骤时会重新构建快照。Task Agent 不能重新选择 SOP 或改变 TaskFrame 顺序。

#### 能力如何进入可调用清单

| 能力配置 | Task Agent 是否可见 | 是否必须执行 |
|---|---|---|
| `general` 且当前员工可用 | 通常可发现 | 否，由模型按需判断 |
| `sop_specific`，但当前节点未引用 | 不可见 | 否 |
| `sop_specific`，当前节点可选引用 | 可见 | 否，由模型按需判断 |
| 当前节点标为 required，且成功编译进 TaskRequirement | 可见 | 是，成功前不得 completed |
| 已停用、解绑、越权或不允许当前 SOP 使用 | 不可调用 | 否，运行时拒绝 |

Task Agent 使用渐进式能力发现：紧凑目录中的能力需要先通过 `capability_describe` 加载完整 Schema 后才能调用；目录不足时可通过 `capability_search` 搜索。每次真实调用前，服务端还会重新检查能力是否仍然启用和授权。

> [!WARNING]
> required 引用不可用时应视为配置错误并在上线前阻断。当前实现会把不可用引用记录在能力快照中，但工具/通用技能和知识库的完成阻断行为并不完全相同；排障时必须检查 `unavailable_references` 和实际生成的 `TaskRequirement`，不能只看编辑器中的 required 标记。

#### 一次执行循环

```text
读取 TaskRequirement
  -> 判断是否缺少阻塞信息
  -> 必要时描述并激活能力
  -> 每轮最多调用一个工具
  -> 读取真实 tool_result
  -> 更新槽位和执行证据
  -> 检查硬约束，并由模型判断一般完成条件
  -> completed / awaiting_user / handoff / failed
```

> [!IMPORTANT]
> 模型不能声称调用了未实际执行的工具。HTTP/MCP 写操作会留下持久化 invocation 记录；远端结果未知时，运行时不会把它当作明确失败后自动安全重试。

#### 通用技能、知识库和工具的区别

- **通用技能**：先 `read` 读取技能包，再决定按规范处理还是确有必要执行脚本；不能跳过读取直接执行。
- **知识库**：用于取得有引用依据的事实；单个 TaskFrame 的有效检索有预算限制，证据足够时应停止扩展检索。
- **HTTP/MCP 工具**：执行查询或业务动作，参数必须符合 Schema，并受当前员工、SOP、步骤和工具配置共同约束。
- **文件/命令能力**：只在隔离 workspace 中操作，不能猜测或访问宿主机路径。

### 3.6 阶段五：状态更新和 SOP 推进

Task Agent 和调度引擎会产生以下执行结果。执行结果不总是等于数据库中的持久化 TaskFrame 状态：

| 状态 | 含义 | 会话后续行为 |
|---|---|---|
| `completed` | 模型声明完成，且当前硬校验通过 | 应用槽位更新，并按允许迁移推进或结束 |
| `awaiting_user` | 仍缺少无法可靠取得的必要信息 | 保存状态并向用户提出具体问题 |
| `handoff` | 当前步骤需要人工处理 | SOP frame 只有 handoff 节点或 `handoff_human` 允许时生效 |
| `failed` | 无法安全完成当前任务 | 保存错误，不伪造结果 |
| `action_budget` | Task Agent 或共享轮次动作预算耗尽 | 未完成，持久化 TaskFrame 通常重新变为 queued |
| `blocked` | 调度引擎发现前置依赖尚未完成 | 不进入 Task Agent；持久化 TaskFrame 通常保持 queued |

`next_step_id` 只能来自当前节点配置的允许迁移。即使模型认为另一个节点“更合理”，也不能跳到未连接节点。服务端硬校验邻接关系，但普通连线的 `condition` 文本主要由模型判断；只有单一出边或明确的 default/else 出边时，运行时可能自动选择下一步。

### 3.7 阶段六：生成最终回复和投递

所有本轮可执行 TaskFrame 处理后，Response Generator 根据任务结果、引用和产物合成用户可见回复。它不应把未执行动作写成已完成，也不负责重新选择 SOP。

回复路径取决于会话来源：

- 网页聊天：直接通过普通或流式接口返回；
- 外部渠道：assistant 消息先写入 `ChannelDelivery` outbox，再投递到原私聊或原群聊；
- 定时任务：结果保存在独立运行会话和运行记录中，不会自动发送给任意渠道联系人。

### 3.8 一个完整例子：退款申请如何执行

假设当前员工已经启用“企业客户退款” SOP，用户发送：

```text
我要退订单 A1008，商品还没有发货。
```

运行过程如下：

| 阶段 | 系统行为 | 可观察结果 |
|---|---|---|
| Planner | 从当前员工 `available_sops` 中匹配退款 SOP | 创建 SOP TaskFrame，不选择退款工具 |
| 服务端规范 | 确认 SOP 仍可用，并指定起始节点 | 模型不能自行从“提交退款”节点开始 |
| TaskRequirement | 合并用户给出的订单号和商品状态 | 已知字段不再追问，只保留真正缺失信息 |
| 查询节点 | required 订单查询工具进入能力清单 | 工具必须成功，才可完成该节点 |
| 工具结果 | 返回订单已支付、未发货、可进入政策校验 | 结果写入 invocation 和 TaskFrame 证据 |
| 政策节点 | 检索售后政策并核对退款资格 | 证据不足时不能承诺退款 |
| 确认节点 | 向用户展示金额和影响，等待明确确认 | 通常以确认槽位和节点指令实现，状态变为 `awaiting_user` |
| 用户确认后 | 继续原 TaskFrame，进入允许的提交节点 | 不创建重复退款任务 |
| 提交节点 | 调用仅限 SOP 的 required 退款工具 | 成功后保存申请单号；结果未知时不盲目重试 |
| 回复生成 | 汇总真实结果和下一步 | 告知申请单号，不泄露内部 Trace |

```text
TaskFrame: refund-A1008
当前步骤: 查询订单
已知槽位: order_id=A1008, shipping_status=not_shipped
必需能力: order_lookup
允许下一步: policy_check | explain_ineligible
执行结果: order_lookup succeeded
下一步: policy_check
```

### 3.9 SOP 固定什么，模型可以判断什么

| SOP/服务端固定的边界 | 模型可以在边界内判断 |
|---|---|
| 当前可候选的已启用 SOP 集合 | 哪个候选最符合本轮用户意图 |
| 新 SOP 的起始节点和进行中任务的当前节点 | 当前消息是继续、切换、澄清还是新建任务 |
| 节点目标、必需槽位和完成条件文本 | 如何自然追问，以及如何判断一般业务条件 |
| 已编译的 required 能力必须成功 | 可选能力是否有必要调用 |
| `sop_specific` 能力必须由当前节点引用 | 在可见能力中选择最合适的一个 |
| 下一节点只能来自允许连线 | 根据真实结果和条件文本选择哪条允许迁移 |
| 权限、沙箱、网络和工具 Schema | 在合法参数范围内构造调用 |
| 工具返回和持久化状态是事实源 | 如何把事实组织成用户可理解的回复 |

### 3.10 运行时默认模型

未在本次请求中指定 `model_config_id` 时，`model_for_agent()` 会忽略员工 ID 和模型角色，统一解析租户中“已启用且设为默认”的模型。有效且已启用的请求级 `model_config_id`（包括网页聊天的模型选择）会覆盖默认值，并用于该轮 Planner、Harness 和回复。切换员工会改变员工画像、SOP 和能力集合，但不会切换到员工专属模型。

管理员可从左侧导航 **模型** 进入 `/enterprise/models`：

| 按钮/控件 | 操作结果 | 影响等级 | 注意事项 |
|---|---|---:|---|
| **刷新** | 重新读取模型配置 | U | 不改变运行时 |
| **新建模型** | 打开模型配置表单 | U，保存后 D/I | 配置协议、Base URL、Model、密钥和生成参数 |
| **启用** | 启用模型；保存前进行连接验证 | I | 默认模型和请求级覆盖模型都必须处于启用状态 |
| **设为默认/已默认** | 设为租户默认模型 | D/I | 影响未显式指定 `model_config_id` 的后续任务 |
| **测试/正在测试** | 验证模型连接 | E | 不执行业务 SOP |
| **编辑** | 修改协议、地址、模型和生成参数 | D/I | 可能影响所有员工输出，应先测试 |
| **删除** | 删除模型配置 | I | 删除默认或唯一可用模型前准备替代配置 |
| **搜索/清除/分页** | 只改变列表显示 | U | 不影响运行时 |

SOP 工作台中的“模型选择”只决定本次 SOP 生成或改写使用哪个模型配置，不会将它设为运行时默认模型。

### 3.11 常见问题

#### 多个 SOP 同时匹配怎么办？

Planner 根据候选摘要和当前上下文选择。若用户明确要办理 SOP，但多个候选无法区分，应返回 `clarify` 请求用户确认，而不是把多个流程私自合并。

#### 没有匹配 SOP 时模型还会回答吗？

会。系统创建 `conversation` TaskFrame，仍经过 Harness 执行普通咨询、计算、文件处理或其他需求，但不会伪造一个不存在的 SOP。

#### 缺少用户信息时会直接追问吗？

不一定。如果授权工具或知识库可以可靠取得相关信息，Task Agent 应先执行能力，再只追问仍会阻塞个性化结论的字段。无法可靠取得时返回 `awaiting_user`。

#### 模型可以跳过 SOP 节点吗？

不能任意跳步。新 SOP 的起始节点、进行中任务的当前节点和允许迁移都由服务端状态机约束。只有配置的连线允许进入下一节点。

#### 模型会修改已发布 SOP 吗？

运行时不会。生成和改写发生在 SOP 编辑工作台，需要用户确认并保存；运行模型只读取当时可用版本并更新会话执行状态。

#### 如何判断 SOP 真正完成？

不能只看回复文字。应检查持久化 TaskFrame 状态、已编译的 required 能力是否成功、必填槽位是否补齐，以及是否产生合法的邻接下一节点或终态。一般 `completion_criteria` 和连线业务条件仍包含模型判断；需要确定性保证的政策条件必须由业务工具、规则服务或审批系统验证。定时任务以 Harness 状态判断成功，不根据自然语言回复猜测。

#### “用户已确认”是系统级审批吗？

不是。普通 SOP 确认通常通过节点指令和 `*_confirmed` 一类槽位表达，运行时可以检查槽位是否存在，但不会独立证明它一定来自合规的明确授权。不可逆操作应由业务 API 使用确认令牌、状态校验、幂等键或专用审批服务进行确定性保护。

#### SOP 执行中被停用会怎样？

SOP 会先从新的路由候选和活动会话投影中移除。已经选中的持久化 SOP frame 如果执行时无法再解析该 SOP，会以 `SOP_NOT_AVAILABLE` 失败；其他不可用 frame 也可能在新计划中被省略，因此需要结合 Trace 判断。能力在调用前被停用或解绑时，调用会被拒绝。

### 3.12 哪些是硬约束，哪些依赖模型判断

| 机制 | 协议生产者 | 服务端硬约束 | 仍依赖模型/配置的部分 |
|---|---|---|---|
| `TurnPlan` | Turn Planner | SOP 必须来自当前候选；任务 ID、步骤和依赖会被规范化 | 候选 SOP 的语义匹配和任务拆分 |
| `TaskFrame` | Planner + 服务端存储 | 状态、租约、依赖、顺序和持久化 | requirements 是否完整表达用户目标 |
| `TaskRequirement` | 服务端编译器 | 必填槽位、已编译 required 能力、允许邻接节点 | 一般完成条件和业务规则文本的解释 |
| `HarnessAction` | Task Agent | 只能调用已激活且仍授权的能力；每轮一个工具 | 选择哪个可选能力及其合法参数 |
| `TaskExecutionResult` | Task Agent + 引擎 | required 调用、已知缺槽和 `next_step_id` 邻接检查 | 一般业务完成判断和连线 condition 判断 |
| 外部副作用 | Harness Invoker + 业务系统 | 授权复核、调用记录和结果未知保护 | 审批、业务资格、确认真实性需业务系统保证 |

## 5. SOP 创建与编辑工作台

入口：`/enterprise/skills/distill`。该页面同时支持自然语言生成、局部改写、源码结构编辑和流程图编辑。

### 5.1 生成区与对话区按钮

| 按钮/控件 | 操作结果 | 影响等级 | 说明 |
|---|---|---:|---|
| **输入流程说明** | 形成生成或改写指令 | D | 指令会直接影响模型生成结果 |
| **上传附件** | 把附件内容作为生成上下文 | D | 附件中的事实和流程会影响草稿；上传本身不保存 SOP |
| **移除附件** | 从本次生成上下文移除 | D | 未发送前生效 |
| **模型选择** | 选择生成/改写使用的模型配置 | D | 影响生成质量、风格和成本，不直接改变运行时业务模型配置 |
| **发送/生成** | 调用流式生成或局部改写接口 | D | 会产生新的本地草稿或待确认改动 |
| **停止生成** | 中止当前流式任务 | E | 不发布不完整内容；检查页面当前草稿状态 |

| **复制消息** | 复制文本到剪贴板 | U | 不改变系统状态 |
| **重新编辑历史消息** | 回到该消息发送前的草稿并截断之后推理，再重新提交 | D | 会重新调用模型，后续草稿可能变化 |
| **取消重新编辑** | 放弃本次历史消息修改 | U | 不调用模型 |

生成建议写法：

```text
业务目标：处理企业客户退款申请。
触发范围：用户明确提出退款、退货或取消已支付订单。
必须收集：订单号、申请原因、商品状态、联系方式。
执行步骤：确认身份 -> 查询订单 -> 校验政策 -> 用户确认 -> 提交退款 -> 告知结果。
禁止事项：未查询订单前不得承诺退款；高风险或工具失败时转人工。
必需能力：订单查询工具、退款申请工具、售后政策知识库。
输出要求：每轮只追问仍缺失的必要信息；工具返回后如实反馈。
```

避免只写“做一个退款 SOP”。过短指令会把关键边界交给模型自行推断。

### 5.2 局部改写的目标选择

工作台可选择一个或多个字段/区域作为改写目标。

| 控件 | 作用 | 影响等级 |
|---|---|---:|
| **选择某字段/节点作为目标** | 限制本次改写路径 | D |
| **全选目标** | 允许模型改写更大范围 | D |
| **清除目标/取消全选** | 移除已选改写范围 | D |

目标范围越大，非预期改动越多。小修改优先只选目标字段或目标节点。

### 5.3 改写结果确认

| 按钮 | 操作结果 | 影响等级 | 是否已写入后端 |
|---|---|---:|---|
| **确认改写** | 把模型返回的新内容应用到当前本地草稿 | D | 否，还需“保存 SOP 版本” |
| **拒绝改写** | 丢弃待确认改动 | U | 否 |

确认改写不等于上线。只有保存并处于启用状态后，未来会话才可能使用新内容。

### 5.4 工具建议

模型生成 SOP 时可能建议新增工具。

| 按钮 | 操作结果 | 影响等级 | 注意事项 |
|---|---|---:|---|
| **查看工具详情** | 展示建议定义 | U | 不创建工具 |
| **探测/测试** | 使用测试参数检查工具 | E | 可能向外部地址发测试请求，需使用无副作用参数 |
| **确认/添加** | 创建或绑定建议工具，并更新相关引用 | I | 增加运行时能力，必须复核 URL、方法、参数和权限 |
| **拒绝** | 不采纳建议 | U | SOP 草稿保持不变 |

不要因为模型建议了一个工具就直接确认。至少检查：

1. URL 和域名是否属于可信业务系统；
2. HTTP 方法是否会产生写操作；
3. 鉴权密钥是否通过安全配置注入；
4. 参数 Schema 是否能限制模型输入；
5. 是否需要业务侧幂等键；
6. 是否应设为“仅限 SOP”；
7. 测试请求会不会创建订单、发消息或扣款。

### 5.5 工作台底部操作

| 按钮 | 操作结果 | 影响等级 | 注意事项 |
|---|---|---:|---|

| **保存 SOP 版本** | 打开保存审阅并持久化当前结构 | D/I | 新建 SOP 会以 `published` 保存；编辑既有 SOP 时保留其原状态 |
| **取消** | 关闭保存审阅 | U | 不持久化 |
| **保存** | 创建或更新 SOP 和版本 | D/I | 保存前务必逐项审阅差异 |

重要：开放 API 的草稿流程明确要求“草稿校验后再发布”，但当前企业编辑器新建 SOP 时会提交 `published` 状态；编辑既有 SOP 时保留原状态。因此新建后的第一次保存应视为直接启用，不能当作普通自动保存。

## 6. 每个 SOP 字段如何影响决策

### 6.1 基本字段

| 字段 | 用途 | 影响等级 | 编写要求 |
|---|---|---:|---|
| **SOP 名称** | 人员识别、候选摘要和展示 | I | 使用清晰业务动作名，如“企业客户退款” |
| **Skill ID/SOP ID** | 稳定标识和版本关联 | I | 发布后保持不变，不用自然语言频繁改 |
| **版本** | 版本审计和回滚 | U/I | 使用一致的版本规则 |
| **业务域** | 分类和候选说明 | I | 使用稳定域名，如售后、财务、人事 |
| **描述** | 说明适用范围 | D/I | 同时写“适用”和“不适用”边界 |
| **步骤超时** | 限制执行等待时间 | E | 外部系统慢时需与工具超时一起评估 |

#### 哪些基础字段会送给模型

这里需要区分**路由模型**和**执行模型**。系统不会把整个 SkillCard 的所有基础字段原样放进每一次模型请求。

在每轮开始的 Turn Planner/SOP 路由阶段，当前代码为每个可用 SOP 构造精简候选信息，只包含：

```json
{
  "skill_id": "skill_expense_quota_query",
  "name": "报销额度查询",
  "description": "识别用户查询报销额度的意图，收集员工工号与查询月份并返回结果。",
  "trigger_intents": ["查询报销额度", "查本月报销剩余额度"]
}
```

因此，当前实现中各基础字段对模型的实际影响如下：

| 字段 | 是否直接进入 SOP 路由模型 | 实际影响 |
|---|---|---|
| **SOP 名称** | 是，字段名为 `name` | 帮助模型理解候选流程是什么；名称应描述业务动作，不要只写内部编号 |
| **Skill ID/SOP ID** | 是，字段名为 `skill_id` | 作为候选的稳定标识；模型可以选择它，但不能靠修改 ID 改变流程含义 |
| **版本** | 否 | 不参与当前意图判断，主要用于版本审计、发布和回滚 |
| **业务域** | 否 | 当前不会作为独立字段送入 SOP 路由模型；可以写入描述帮助模型理解，但不要把业务域当作可靠路由条件 |
| **描述** | 是 | 直接帮助模型判断用户请求是否属于该 SOP；应写适用范围、核心对象和不适用边界 |
| **步骤超时** | 否 | 不用于意图判断；由执行/调度约束等待时间 |

`user_utterance_examples` 当前也不会作为独立字段放入 SOP 路由候选 payload。它适合帮助编辑人员完善 SOP 和生成内容，但如果某种说法对路由非常关键，应同时写入 `trigger_intents` 或 `description`，不要只依赖示例字段。

路由阶段真正优先参考的是：

1. 用户当前消息；
2. 当前会话中的活动 SOP、步骤和 slots；
3. 可用 SOP 的 `name`、`description`、`trigger_intents`；
4. 其他由系统提供的上下文，例如待处理任务和会话状态。

路由选中 SOP 后，执行模型看到的是另一组信息。服务端会把当前节点编译为 TaskRequirement，通常包括当前节点的 `instruction`、尚未满足的 `expected_user_info`、当前 SOP 的 `goal`、当前已保存的 slots、允许动作和当前节点授权的工具/技能/知识库。此时，节点指令、目标、必需信息、回复规则和能力引用才会直接约束执行。

回复生成阶段还会读取当前 SOP 的 `response_rules`，以及工具结果、知识检索结果、当前节点和已收集 slots，用于生成最终用户回复。也就是说，基础字段主要影响“选哪个 SOP”，而节点和全局执行字段主要影响“当前这一步怎么做、何时完成、如何回复”。

> 编写建议：如果要提高“报销额度查询”被选中的概率，应把“查询员工报销总额度、已用额度和剩余额度”写进 `description`，把“查询报销额度、查本月还剩多少”等写进 `trigger_intents`；不要只写在 `user_utterance_examples` 或 `business_domain` 中。

### 6.2 路由字段

| 字段 | 用途 | 影响等级 | 风险 |
|---|---|---:|---|
| **触发意图** | 帮助 Planner 判断是否启动 SOP | D | 过宽会误触发，过窄会漏触发 |
| **用户说法示例** | 提供典型表达 | D | 应包含口语、同义词和边界反例 |

推荐：触发意图写成“用户要完成什么业务动作”，而不是工具名。不要写“调用退款 API”，应写“用户希望对已支付订单申请退款”。

### 6.3 全局执行字段

| 字段 | 用途 | 影响等级 | 编写要求 |
|---|---|---:|---|
| **目标** | 定义 SOP 最终要达到的结果 | D | 可验证，不写空泛口号 |
| **必需信息** | 定义流程需要的稳定字段 | D | 只收真正阻塞办理的信息 |
| **回复规则** | 约束用户可见回复 | D | 明确禁止承诺、敏感信息和格式要求 |

### 6.4 节点字段

| 字段 | 用途 | 影响等级 | 编写要求 |
|---|---|---:|---|
| **节点名称** | 人员阅读和 Trace 定位 | I | 使用动作名，如“查询订单” |
| **节点 ID/步骤 ID** | 状态机定位 | I | 已上线流程中保持稳定 |
| **节点类型** | 区分处理、收集、结束、转人工等节点 | D/I | 与实际动作一致 |
| **节点指令** | 当前 TaskFrame 的核心执行说明 | D | 写输入、动作、成功条件和失败处理 |
| **期待用户信息** | 形成当前节点缺失槽位 | D | 缺失且无法可靠获取时会追问用户 |
| **允许动作** | 限制当前节点能做什么 | I | 转人工必须显式允许 `handoff_human` 或使用 handoff 节点 |
| **重试策略** | 控制失败后的尝试 | E | 有副作用动作不可盲目重试 |

### 6.5 能力引用

每个节点可引用工具、通用技能和知识库，并区分可选与必需：

- **可选引用**：能力出现在当前步骤的授权清单中，模型按需决定是否调用；
- **必需引用**：该能力必须成功执行，否则 TaskFrame 不能标记完成；
- **不可用引用**：资源停用、解绑、越权或范围不符时，运行时不会尝试绕过授权。

| 配置 | 影响等级 | 结果 |
|---|---:|---|
| 添加可选工具 | I | 模型在当前步骤可以选择调用 |
| 添加必需工具 | D/I | 完成前必须成功调用 |
| 添加可选知识库 | I | 模型可按需要检索 |
| 添加必需知识库 | D/I | 完成前必须完成要求的检索 |
| 添加通用技能 | I | 模型先读取技能说明，再决定是否执行脚本或按规范处理 |
| 移除引用 | I | 当前步骤不可再依赖该引用；`general` 能力仍可能因全局可见而被自主调用 |

### 6.6 “通用/仅限 SOP”开关

工具、技能和知识库编辑器中的“能力范围”开关非常重要：

| 值 | 运行时含义 | 影响等级 |
|---|---|---:|
| **通用** | 普通对话和 SOP 执行中均可能被模型自主调用 | I |
| **仅限 SOP** | 只有当前 SOP 节点明确引用时才加入可调用清单 | I |

高风险写操作工具、特定流程知识和专用技能优先设为“仅限 SOP”。仅设置“仅限 SOP”还不够，必须在正确节点中显式引用，否则模型看不到该能力。

## 7. 节点和连线的推荐写法

### 7.1 单节点模板

```text
节点名称：查询订单
节点目标：取得订单状态、支付状态和可退款金额。
输入要求：订单号；如用户未提供且无法从上下文可靠取得，只追问订单号。
执行动作：必须调用 order_lookup 工具一次。
成功条件：工具返回匹配订单，且关键状态字段完整。
失败处理：无匹配订单时说明未查到并请用户核对；工具异常时不得声称查询成功。
回复边界：本节点不承诺退款结果。
下一步：满足退款校验条件时进入“校验政策”，否则进入“说明不可办理”。
```

### 7.2 连线条件模板

条件应基于可验证状态，不应写含糊的“如果合适”：

- `订单存在且支付状态为已支付`；
- `政策检索结果明确允许退款`；
- `用户已明确确认提交`；
- `工具返回成功且包含申请单号`；
- `工具失败或风险等级超过阈值`。

### 7.3 用户确认节点

对于下单、退款提交、发信、修改业务数据等副作用动作，建议在工具调用前设置独立确认节点：

1. 汇总即将执行的动作和关键参数；
2. 明确询问用户是否确认；
3. 只有获得本轮明确确认后，进入写操作节点；
4. 写操作节点引用“仅限 SOP”的必需工具；
5. 工具结果未知时不自动重复提交，转人工或提示核验。

这是 SOP 设计模式，不是系统级通用审批。对于合规场景仍需业务工具或外部系统提供真正审批。

## 8. 版本管理与发布 SOP

2. 点击 **版本管理**。

4. 点击 **查看详情**检查元数据和内容。

## 8A. SOP Open API 快速调用

StaffDeck Open API v1 可用于自动生成、局部改写、校验、发布、归档和回滚员工 SOP。API 自动化与企业编辑器最大的区别是：**所有生成、改写、结构化创建和回滚都先产生员工私有草稿，必须显式发布后才参与模型路由和执行。**

> [!TIP]
> 本节只提供最小可运行链路。完整环境、凭证、Run、Webhook 和其他资源说明见 [`docs/open-api-v1.md`](./open-api-v1.md)。接口 Schema 以当前环境的 `/api/v1/docs` 和 `/api/v1/openapi.json` 为准。

> [!IMPORTANT]
> 普通员工“运行密钥”只有会话、Run、Trace 和产物权限，不能修改 SOP。管理 SOP 需要账号全量密钥，或未绑定 `agent_id`、具备 `sops:read`、`sops:write`、`sops:publish` 且其所有者有目标员工写权限的租户级 API Credential。

> [!WARNING]
> 密钥明文只在创建或轮换时返回一次。不要把真实 `sd_live_...` 写入脚本、SOP、截图、Git 或日志。示例统一从环境变量读取。

### 8A.1 接口总览

Base URL 统一以 `$BASE` 表示，例如：

```bash
export BASE="https://staffdeck.example/api/v1"
export STAFFDECK_API_KEY="sd_live_xxx"
export AGENT_ID="agent_xxx"
```

所有 JSON 请求使用：

```http
Authorization: Bearer <STAFFDECK_API_KEY>
Content-Type: application/json
```

请求体不传 `tenant_id`。服务端从 Credential 推导租户、操作者、scope 和员工边界。

| 操作 | 方法与路径 | Scope | 结果 |
|---|---|---|---|
| 列出已发布 SOP 和草稿 | `GET /agents/{agent_id}/sops` | `sops:read` | HTTP 200：`data`、`drafts` |
| 结构化创建草稿 | `POST /agents/{agent_id}/sops` | `sops:write` | HTTP 201：Draft + `ETag` |
| 从文本生成草稿 | `POST /agents/{agent_id}/sops:generate` | `sops:write` | HTTP 202 Job |
| 局部改写 | `POST /agents/{agent_id}/sops/{sop_id}:rewrite` | `sops:write` | HTTP 202 Job |
| 读取草稿 | `GET /agents/{agent_id}/sops/{sop_id}/drafts/{draft_id}` | `sops:read` | HTTP 200：Draft + `ETag` |
| 完整替换草稿 | `PUT /agents/{agent_id}/sops/{sop_id}?draft_id=...` | `sops:write` | HTTP 200：更新原 Draft + 新 `ETag` |
| JSON Patch 草稿 | `PATCH /agents/{agent_id}/sops/{sop_id}?draft_id=...` | `sops:write` | HTTP 200：更新原 Draft + 新 `ETag` |
| 校验草稿 | `POST /sops/{sop_id}:validate?agent_id=...&draft_id=...` | `sops:write` | HTTP 200：`valid`、错误和警告 |
| 发布草稿 | `POST /sops/{sop_id}:publish?agent_id=...` | `sops:publish` | HTTP 200：已发布 SOP 和 Draft |
| 归档 SOP | `POST /sops/{sop_id}:archive?agent_id=...` | `sops:publish` | HTTP 200：已归档 SOP |
| 查看版本/差异 | `GET /sops/{sop_id}/versions...` | `sops:read` | HTTP 200：版本或 JSON Diff |
| 创建回滚草稿 | `POST /sops/{sop_id}/versions/{version}:rollback?agent_id=...` | `sops:write` | HTTP 201 Draft |

> **截图占位 A01｜创建账号 API 全量密钥**  
> 页面：StaffDeck 右上角用户菜单 → **API 全量密钥**。  
> 范围：用户菜单、账号全量密钥弹窗、创建按钮和一次性密钥提示。  
> 标注：① API 全量密钥；② 创建；③ 一次性明文；④ 轮换；⑤ 禁用。截图必须遮盖密钥。

### 8A.2 完整调用链

```text
准备管理 Credential 和 agent_id
  -> POST 生成 SOP Job
  -> GET Job，等待 succeeded
  -> GET Job result，保存 sop_id、draft_id
  -> GET Draft，保存最新 ETag
  -> PATCH/PUT 修改草稿（If-Match）
  -> POST validate
  -> 人工或发布流程确认
  -> POST publish
  -> GET SOP/versions 复核发布版本
```

> [!NOTE]
> 下面使用“从文本生成”作为示例。已有完整 `SkillCard` 时可直接结构化创建；小范围修改优先使用 rewrite 或 JSON Patch，不要无条件覆盖整个草稿。

### 步骤 1：从文本生成 SOP 草稿

`POST /agents/{agent_id}/sops:generate`

| 参数 | 位置 | 必填 | 说明 |
|---|---|---:|---|
| `agent_id` | Path | 是 | 目标数字员工 ID |
| `title` | Body | 是 | SOP 标题，1 至 200 字符 |
| `raw_content` | Body | 是 | 原始业务流程和约束 |
| `business_domain` | Body | 否 | 业务域，例如 `after_sales` |
| `model_config_id` | Body | 否 | 指定生成模型；不传时使用运行时解析规则 |
| `Idempotency-Key` | Header | 建议 | 外部系统本次生成请求的唯一 ID |

```bash
curl --fail-with-body -X POST "$BASE/agents/$AGENT_ID/sops:generate" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY" \
  -H "Idempotency-Key: sop-generate-refund-v1" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "企业客户退款",
    "business_domain": "after_sales",
    "raw_content": "处理已支付订单退款。先查询订单和政策，收集必要信息，提交前必须确认；工具失败或结果未知时不得承诺成功。"
  }' | tee /tmp/staffdeck-sop-job.json

export JOB_ID="$(jq -er '.id' /tmp/staffdeck-sop-job.json)"
```

HTTP 202 响应只表示 Job 已创建，不表示 SOP 已生成。以下为响应节选，完整 `JobRead` 还包含 `session_id`、`retryable`、`error` 和时间戳：

```json
{
  "id": "apijob_xxx",
  "kind": "sop.generate",
  "status": "queued",
  "stage": "queued",
  "progress": 0,
  "agent_id": "agent_xxx"
}
```

> [!IMPORTANT]
> 保存响应中的 `id` 为 `$JOB_ID`。以上示例需要本机安装 `jq`。重复请求时使用相同 `Idempotency-Key` 和相同 Body；同一个 Key 携带不同内容会返回 `409 IDEMPOTENCY_CONFLICT`。

### 步骤 2：等待生成 Job 完成

`GET /jobs/{job_id}`

```bash
curl --fail-with-body "$BASE/jobs/$JOB_ID" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY"
```

Job 终态为 `succeeded`、`failed` 或 `cancelled`。只有 `succeeded` 后才读取并使用结果；客户端应使用有上限的退避轮询，不要无限高频请求。

也可以订阅 SSE：

```bash
curl --fail-with-body -N "$BASE/jobs/$JOB_ID/events" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY" \
  -H "Accept: text/event-stream"
```

断线续传可携带 `Last-Event-ID`。自定义租户级 Credential 只有具备 `jobs:cancel` 或 `sops:cancel` 时，才能取消尚未结束的 SOP Job：

```http
POST /jobs/{job_id}:cancel
```

取消是协作式请求，不保证立即中断正在执行的模型调用。`sop.generate` 或 `sop.rewrite` 可能先创建私有草稿，随后 Job 才显示 `cancelled`；取消后应调用 `GET /agents/{agent_id}/sops` 检查并审阅遗留草稿。

### 步骤 3：读取结果并保存草稿标识

`GET /jobs/{job_id}/result`

```bash
curl --fail-with-body "$BASE/jobs/$JOB_ID/result" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY" \
  | tee /tmp/staffdeck-sop-result.json

export SOP_ID="$(jq -er 'select(.job.status == "succeeded") | .result.draft.sop_id' /tmp/staffdeck-sop-result.json)"
export DRAFT_ID="$(jq -er 'select(.job.status == "succeeded") | .result.draft.id' /tmp/staffdeck-sop-result.json)"
```

生成成功后，`result.draft` 中包含后续操作需要的字段。以下为响应节选：

```json
{
  "job": {
    "id": "apijob_xxx",
    "status": "succeeded"
  },
  "result": {
    "draft": {
      "id": "draft_xxx",
      "agent_id": "agent_xxx",
      "sop_id": "enterprise_refund",
      "draft_version": "1.0.0",
      "status": "draft",
      "etag": "\"etag_xxx\""
    },
    "tool_suggestions": []
  },
  "error": {}
}
```

> [!IMPORTANT]
> 同时保存 `draft.id`、`draft.sop_id` 和 `draft.etag`。`GET /jobs/{job_id}/result` 在 Job 未结束时返回 `409 JOB_NOT_FINISHED`；`failed` 和 `cancelled` 则返回 HTTP 200 的结果信封。只有 `job.status == "succeeded"` 时才使用 `result.draft`，失败信息位于 `error`。

### 步骤 4：读取草稿和最新 ETag

`GET /agents/{agent_id}/sops/{sop_id}/drafts/{draft_id}`

```bash
curl --fail-with-body "$BASE/agents/$AGENT_ID/sops/$SOP_ID/drafts/$DRAFT_ID" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY" \
  | tee /tmp/staffdeck-sop-draft.json

export DRAFT_ETAG="$(jq -er '.etag' /tmp/staffdeck-sop-draft.json)"
```

响应 Body 返回完整草稿，响应头和 Body 都包含当前 ETag。更新前优先使用本次读取响应头中的值：

```http
ETag: "current-etag"
```

`DRAFT_ETAG` 必须保留值本身的双引号，并原样使用 `-H "If-Match: $DRAFT_ETAG"`。不要再次给 ETag 值增加一层引号，也不要移除其 HTTP 引号。

> **截图占位 A02｜API 草稿与运行版本的边界**  
> 页面：左侧展示 `/jobs/{id}/result` 或 OpenAPI 中的 Draft 响应，右侧展示 `http://127.0.0.1:5173/enterprise/skills`。  
> 范围：API 返回的 `status: draft`、`draft_id`，以及员工 SOP 页面中尚未出现该运行版本的列表。  
> 标注：① API 私有草稿；② Draft ID；③ 员工运行 SOP 列表；④ 未发布草稿不会在企业 SOP 页面显示。可在附图中补充开放广场卡片，但不要伪造页面上的 API 草稿状态。

### 步骤 5：使用 JSON Patch 修改草稿

`PATCH /agents/{agent_id}/sops/{sop_id}?draft_id={draft_id}`

小范围修改优先使用 JSON Patch，并携带最新 `If-Match`：

```bash
curl -X PATCH "$BASE/agents/$AGENT_ID/sops/$SOP_ID?draft_id=$DRAFT_ID" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY" \
  -H "If-Match: $DRAFT_ETAG" \
  -H "Content-Type: application/json-patch+json" \
  -d '[
    {
      "op": "replace",
      "path": "/description",
      "value": "处理已支付且符合售后政策的企业客户退款申请"
    }
  ]'
```

成功后服务端原地更新同一个 Draft，`draft_id` 不变，并返回新 `ETag`。后续每次更新都必须改用最新 ETag。

| 更新方式 | 适用场景 | 关键约束 |
|---|---|---|
| `POST ...:rewrite` | 用自然语言局部改写一个或多个路径 | 异步 Job；可传 `draft_id` 和 `target_paths` |
| `PATCH` | 精确修改少量字段 | `application/json-patch+json` + `If-Match` |
| `PUT` | 完整 SkillCard 是唯一权威来源 | 会替换整个草稿；`If-Match` 必填 |

> [!WARNING]
> `skill_id` 不可修改。缺少 `If-Match` 返回 `428 IF_MATCH_REQUIRED`；草稿已被其他人更新时返回 `412 ETAG_MISMATCH`。收到 412 后重新读取最新草稿并合并，不要盲目覆盖。

### 步骤 6：校验草稿

`POST /sops/{sop_id}:validate?agent_id={agent_id}&draft_id={draft_id}`

```bash
curl -X POST \
  "$BASE/sops/$SOP_ID:validate?agent_id=$AGENT_ID&draft_id=$DRAFT_ID" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY"
```

```json
{
  "valid": false,
  "errors": [
    {
      "path": "capability_refs.tool",
      "code": "CAPABILITY_UNAVAILABLE",
      "detail": "tool tool_xxx is not active and bound to this agent."
    }
  ],
  "warnings": []
}
```

校验会检查 SkillCard 结构，以及节点引用的工具、通用技能和知识库是否属于同一租户、已绑定当前员工且处于可用状态。

> [!IMPORTANT]
> 只有 `valid: true` 才进入发布步骤。校验通过不代表业务规则已经获得合规审批，写操作权限、用户授权、确认令牌和业务幂等仍由工具或外部系统保证。

### 步骤 7：显式发布已校验草稿

`POST /sops/{sop_id}:publish?agent_id={agent_id}`

```bash
curl -X POST "$BASE/sops/$SOP_ID:publish?agent_id=$AGENT_ID" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY" \
  -H "Content-Type: application/json" \
  -d "{\"draft_id\":\"$DRAFT_ID\"}"
```

发布接口会重新校验指定草稿。校验失败返回 `422 SOP_VALIDATION_FAILED`；成功后该员工的已发布 SOP 才会进入未来路由候选。

> [!WARNING]
> 发布必须使用操作者明确确认的 `draft_id`。不要“自动选择最新草稿”后直接发布，也不要把生成 Job 成功等同于发布成功。

> [!WARNING]
> Publish、archive 和 rollback 当前不受公共幂等存储保护。发布响应丢失时，先查询 SOP 列表和版本再决定是否重试；同一个已发布 Draft 再次 publish 可能返回 `SOP_DRAFT_NOT_FOUND`。重复 rollback 会创建多个回滚草稿。

### 步骤 8：复核版本和运行状态

```bash
curl "$BASE/sops/$SOP_ID/versions?agent_id=$AGENT_ID" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY"
```

发布后重新读取 SOP 列表，确认：

1. `data` 中出现目标 SOP；
2. 版本号符合预期；
3. 目标员工正确；
4. 草稿状态已变为 published；
5. 用自然语言和 `/sop` 各执行一次回归测试。

> **截图占位 A03｜API 发布后在员工 SOP 列表复核**  
> 页面：`http://127.0.0.1:5173/enterprise/skills`  
> 范围：目标员工、SOP 名称、版本、已启用状态和版本管理入口。  
> 标注：① 目标员工；② SOP ID；③ 版本；④ 已启用；⑤ 版本管理。

### 8A.3 版本差异和回滚

查看两个已发布版本的差异：

```bash
curl "$BASE/sops/$SOP_ID/versions/1.1.0/diff?agent_id=$AGENT_ID&compare_to=1.0.0" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY"
```

回滚不会立刻替换运行版本，而是从历史版本创建一个新草稿：

```bash
curl -X POST \
  "$BASE/sops/$SOP_ID/versions/1.0.0:rollback?agent_id=$AGENT_ID" \
  -H "Authorization: Bearer $STAFFDECK_API_KEY"
```

保存返回的新 `draft_id`，重新校验并显式发布。这让回滚也经过与普通变更相同的审核边界。

### 8A.4 错误与恢复

公共 API 错误使用 `application/problem+json`：

```json
{
  "type": "urn:staffdeck:error:etag_mismatch",
  "title": "ETAG_MISMATCH",
  "status": 412,
  "code": "ETAG_MISMATCH",
  "detail": "The SOP draft changed since it was read.",
  "request_id": "req_xxx"
}
```

| 状态/错误 | 常见原因 | 恢复操作 |
|---|---|---|
| `401` | 密钥缺失、错误、已轮换或禁用 | 获取有效密钥，不在日志中输出原值 |
| `403 INSUFFICIENT_SCOPE` | 缺少要求的 scope | 使用未绑定员工的管理 Credential 并核对 scope |
| `403 AGENT_*` | 员工密钥只读、员工边界不匹配或无管理权限 | 改用账号全量密钥或租户级管理 Credential |
| `404` | 环境、员工、SOP、Draft 或 Job ID 错误；不可见员工也可能故意表现为 404 | 核对 `$BASE`、权限和前一步保存的 ID |
| `409 IDEMPOTENCY_CONFLICT` | 同一 Key 携带不同请求内容 | 不换内容重放；改用新的业务请求 ID |
| `409 JOB_NOT_FINISHED` | Job 仍 queued/running | 继续有上限地轮询，不重建 Job |
| `412 ETAG_MISMATCH` | 草稿被并发修改 | 重新 GET，合并变化后用新 ETag 更新 |
| `422 VALIDATION_ERROR` | 请求字段缺失、为空或类型错误 | 按 `errors` 修复请求 Body |
| `422 INVALID_SOP` | 结构化创建或 PUT 的 SkillCard 图不合法 | 按 `errors` 修复节点、边或字段 |
| `422 INVALID_JSON_PATCH` | Patch 操作或 Patch 后的 SkillCard 不合法 | 检查 JSON Pointer、操作和值 |
| `422 SOP_ID_IMMUTABLE` | 尝试修改 `skill_id` | 恢复原 SOP ID；新 ID 应创建新 SOP |
| `422 SOP_VALIDATION_FAILED` | 能力引用不可用或草稿校验失败 | 修复绑定/状态/引用后重新校验 |
| `428 IF_MATCH_REQUIRED` | PUT/PATCH 未携带 ETag | 读取草稿并添加 `If-Match` |
| Job `failed` | 生成/改写执行失败 | 保存 Job ID、`stage`、`error` 和 `request_id` 后排障 |

客户端可以传 `X-Request-ID`；未传时 StaffDeck 自动生成，并在响应头及错误体中返回。提交工单或查日志时同时提供 `request_id`、`job_id`、`agent_id` 和 `sop_id`，不要提供密钥。

### 8A.5 API 与页面按钮的对应关系

| 页面操作 | Open API | 是否直接影响运行时 |
|---|---|---|
| 新建空白 SOP | `POST /agents/{agent_id}/sops` | 否，只创建草稿 |
| 自然语言生成 | `POST /agents/{agent_id}/sops:generate` | 否，只创建异步草稿 |
| 局部改写 | `POST /agents/{agent_id}/sops/{sop_id}:rewrite` | 否，只创建新草稿 |
| 保存局部修改 | `PATCH` 或 `PUT` 草稿 | 否，仍未发布 |
| 发布/启用 | `POST /sops/{sop_id}:publish` | 是，未来路由可使用 |
| 停用 | `POST /sops/{sop_id}:archive` | 是，从未来路由候选移除 |
| 查看版本 | `GET /sops/{sop_id}/versions` | 否，只读 |
| 回滚 | `POST ...:rollback` | 否，只创建回滚草稿；发布后才生效 |

## 9. SOP 测试与验收

### 9.1 最小测试矩阵

每个上线 SOP 至少测试：

| 场景 | 验证内容 |
|---|---|
| 标准触发 | 典型说法能进入正确 SOP |
| 同义表达 | 不同口语仍能正确路由 |
| 负向边界 | 相似但不适用的请求不会误触发 |
| 信息齐全 | 不重复追问已知字段 |
| 信息缺失 | 只追问真正缺失且阻塞的信息 |
| 工具成功 | 参数正确，结果被如实使用 |
| 工具失败 | 不伪造成功，不无限重试 |
| 知识不足 | 明确说明证据不足或进入合适后续步骤 |
| 用户拒绝 | 不执行副作用动作 |
| 用户确认 | 只在明确确认后执行 |
| 转人工 | 只有允许 handoff 的节点能转人工 |
| 版本切换 | 新版本生效，旧历史记录保留 |
| 停用 | 新会话不再选择该 SOP |
| 并发/重复 | 外部写操作不产生重复提交 |

### 9.2 使用 `/sop` 定向测试

聊天界面支持 `/sop <skill>` 形式的斜杠命令，可用于定向选择 SOP 进行测试。命令选择器的搜索和展开是 U 级操作；命令实际提交后会影响本轮运行时选择。

定向测试不能替代自然语言路由测试，因为它绕过了部分“用户自然表达能否正确匹配”的验证目标。

### 9.3 Trace 重点检查

1. Planner 选择了哪个 SOP，理由是否符合用户意图。
2. TaskFrame 的目标和 requirements 是否遗漏用户附加要求。
3. 当前节点和 required slots 是否正确。
4. 能力清单中是否出现了不该出现的通用工具。
5. `sop_specific` 引用是否在正确节点可见。
6. 必需能力是否实际成功执行。
7. 下一节点是否来自允许连线。
8. 工具参数和结果是否与回复一致。
9. 最终回复是否遵守回复规则。

## 10. 外展方式一：外部用户发起，数字员工沿原会话回复

这是项目内置渠道的标准工作方式：外部用户先发起消息，StaffDeck 再沿原私聊或群聊回复。

> [!IMPORTANT]
> 当前项目没有独立的 Campaign、联系人列表、触达序列或群发页面。渠道页没有收件人输入框、主动发送按钮、历史会话回复框或定时群发按钮。

标准链路如下：

```text
外部用户发消息
  -> 渠道绑定接收入站事件
  -> 当前员工/智能分发选择员工
  -> Planner 选择 SOP
  -> Harness 执行节点和能力
  -> 回复写入 outbox
  -> 投递回原私聊或原群聊
```

- 企业微信；

### 步骤 2：配置智能分发

**智能分发**开关默认开启：

- 开启：独立的 LLM 意图分类器可以在挂载员工中选择员工；

- 少于两名挂载员工时不需要分类；
- 人工接管中不自动分类；
- 用户手动切换后 10 分钟内不自动切换；

- 模型异常、超时、坏 JSON 或低置信度时保持当前员工。

该开关属于 D/I：它会触发路由模型，并可能改变后续使用的员工、员工画像、SOP 和能力集合，但不会切换员工专属模型，也不会改变外发目标。

## 12. 渠道回复、人工接续和日志

### 步骤 1：确认自动回复链路

1. 外部消息形成持久化入站事件并去重。
2. 系统确定当前员工或执行智能分发。
3. Harness v2 执行对话和 SOP。
4. assistant 消息写入数据库。
5. 系统创建 `ChannelDelivery` outbox 记录。
6. 后台适配器发送到原消息对应目标。
7. 状态从待投递变为投递中、已送达或投递失败。

系统使用幂等键和有限重试降低重复发送风险。远端结果不确定时，不应盲目重复外部写操作。

### 步骤 2：处理人工接续

只有当前 SOP 节点显式允许 handoff 时，模型的转人工请求才会生效。

1. 在聊天界面的“待回答”中打开 handoff。
2. 阅读上下文摘要和待处理问题。
3. 可点击 **打开原会话** 查看上下文。
4. 输入人工回复。
5. 点击 **回复并恢复**。

人工输入不会直接裸发到渠道。它会作为恢复输入重新交给 AgentLoop 推进 SOP，最终生成的 assistant 回复再沿原渠道投递。因此该输入属于 D 级，会影响后续模型决策。

当前 handoff 只支持文字，不支持附件或定时任务模式。

> 页面：`http://127.0.0.1:5173/enterprise/channels`  
> 范围：断开接入按钮和确认弹窗。  
> 标注：① 断开接入；② 影响说明；③ 最终确认。

## 13. 外展方式二：通过业务工具主动触达

当业务必须主动联系收件人时，应把“发送”实现为明确授权的业务工具，而不是依赖渠道回复目标。

> [!WARNING]
> 普通渠道绑定只能回复已有入站会话。不要把渠道接入页或定时任务误当成任意联系人发送工具。

### 步骤 1：创建受控发送工具

1. 创建一个只允许目标业务域调用的 HTTP/MCP 工具，例如 `send_customer_message`。
2. 工具输入 Schema 明确定义收件人 ID、渠道、模板 ID、变量和幂等键。
3. 不允许模型自由填写任意 URL、密钥或未验证目标。
4. 将工具能力范围设为 **仅限 SOP**。
5. 只在“用户确认”后的发送节点中引用。
6. 对发送工具设为必需能力，确保未实际发送时任务不能声称完成。
7. 业务系统返回消息 ID、目标、时间和状态，供 Trace 审计。
8. 远端结果未知时转人工核验，不自动重复发送。

> **截图占位 26｜配置主动发送工具**  
> 页面：StaffDeck 工具编辑页。  
> 范围：工具地址、方法、输入 Schema、能力范围和测试区域。  
> 标注：① HTTP/MCP 地址；② 方法；③ 收件人字段；④ 幂等键；⑤ 仅限 SOP。

### 步骤 2：创建主动外展 SOP

```text
节点 1：确定触达目标
- 收集或查询受控的客户 ID，不接受任意未验证地址。

节点 2：校验触达资格
- 查询授权、退订、频控、时段和隐私规则。
- 任一校验不通过则结束，不进入发送节点。

节点 3：生成内容草稿
- 只使用批准模板和受控变量。
- 不允许模型添加未经批准的承诺或营销声明。

节点 4：确认发送
- 展示目标、渠道、内容摘要和可能影响。
- 取得用户本轮明确确认。

节点 5：执行发送
- 必须调用仅限 SOP 的发送工具。
- 使用业务幂等键。
- 记录外部消息 ID。

节点 6：结果反馈
- 成功时返回真实消息 ID和状态。
- 失败时说明错误；结果未知时转人工核验，不重发。
```

> **截图占位 27｜主动外展 SOP 流程图**  
> 页面：`http://127.0.0.1:5173/enterprise/skills/distill?...`  
> 范围：资格校验、内容草稿、确认、发送和结果节点。  
> 标注：① 资格校验；② 用户确认；③ 发送工具；④ 结果未知；⑤ 转人工。

### 步骤 3：完成发送安全检查

- 收件人授权和退订校验；
- 频率和安静时段限制；
- 消息模板及变量白名单；
- 用户确认或外部审批；
- 幂等键；
- 外部消息 ID 和审计日志；
- 失败、超时、结果未知的处理；
- 密钥隔离和最小权限。

> [!IMPORTANT]
> SOP 中的“用户确认节点”是一种流程设计，不是系统级通用审批。受监管场景仍需业务工具或外部系统提供真正的审批、授权和审计。

## 14. 定时任务：定时唤醒员工，不等于定时群发

入口：左侧导航 **定时任务**，路由 `/enterprise/scheduled-tasks`。

> [!NOTE]
> 定时任务会创建独立的内部会话，没有渠道绑定、收件人 ID 或群 ID。只有任务显式调用已授权的业务发送工具时，才可能产生主动外展。

### 步骤 1：新建定时任务

1. 选择一个具体数字员工。
2. 点击 **新增任务**。
3. 填写任务名称。
4. 在“每次执行时交给员工的任务”中写清目标、范围、执行要求、输出和异常处理。
5. 选择每天、每周、每月或一次性。
6. 设置日期、时间和最大执行次数。
7. 确认启用状态后点击 **保存**。

> **截图占位 28｜创建定时任务**  
> 页面：`http://127.0.0.1:5173/enterprise/scheduled-tasks/new`  
> 范围：完整任务编辑表单。  
> 标注：① 任务名称；② 核心任务说明；③ 启用；④ 计划类型；⑤ 时间；⑥ 最大次数；⑦ 保存。

### 步骤 2：理解列表按钮

| 按钮/控件 | 操作结果 | 影响等级 | 模型影响 |
|---|---|---:|---|
| **新增任务** | 打开任务编辑器 | U | 保存后才影响 |
| 任务/运行状态筛选 | 本地筛选 | U | 否 |
| **查看记录** | 查看历史运行 | U | 否 |
| **编辑** | 修改未来执行配置 | D/E | 任务说明改变时直接影响 |
| **立即执行** | 立即创建一次运行 | E，执行时 D | 使用已保存任务说明调用员工 |
| **暂停** | 停止未来定时唤醒 | E | 不改任务说明 |
| **启用** | 恢复未来定时唤醒 | E | 不改任务说明 |
| **删除** | 停止未来执行，保留历史运行 | E | 否 |
| **查看会话** | 新窗口打开该次运行会话 | U | 否 |

> **截图占位 29｜定时任务行操作**  
> 页面：`http://127.0.0.1:5173/enterprise/scheduled-tasks`

### 步骤 3：理解编辑器字段

| 字段/按钮 | 作用 | 影响等级 |
|---|---|---:|
| **任务名称** | 展示和管理名称 | U/I |
| **每次执行时交给员工的任务** | 每次运行的核心模型指令，最多 10000 字符 | D |
| **内部说明** | 记录来源和用途 | U |
| **启用开关** | 保存为 active 或 paused | E |
| **每天/每周/每月/一次性** | 计划类型 | E |
| **日期和时间** | 执行时间 | E |
| **周一至周日** | 每周执行日 | E |
| **每月日期** | 月内日期，1 至 31 | E |
| **最大执行次数** | 设置调度完成阈值 | E |
| **保存** | 创建或更新任务 | D/E |
| **返回定时任务** | 返回列表 | U |

当前企业编辑器默认且固定提交以下值，页面没有修改控件：

- `forbid` 并发策略：上一轮未结束时跳过本次唤醒；
- `coalesce` 错过执行策略：多个错过时间合并处理。

后端 API 还支持 `allow` 并发和 `skip` 错过策略，因此这不是系统级不可变限制；通过 API 修改后以服务端已保存配置为准。

**立即执行**也会创建运行记录并增加 `run_count`，但手动运行不会推进下一次计划时间，也不会在该次结束时立即按 `max_runs` 把任务改为完成；最大次数阈值会在后续非手动运行结束时判断。运营上不要用“立即执行”绕过次数控制，测试任务应使用独立任务或在测试后复核 `run_count`。

定时任务创建独立的内部会话，没有渠道绑定、收件人 ID 或群 ID 字段。它不会自动沿某个历史外部会话发消息。若任务需要主动外展，任务说明必须触发已授权的业务发送工具，并由 SOP/工具执行所有合规控制。

### 步骤 4：编写任务说明

```text
目标：检查今天需要跟进的已授权客户，并为每个客户执行“客户跟进外展” SOP。
范围：只处理 CRM 返回的 opted_in=true 且未退订客户。
执行要求：逐个校验频控和安静时段；使用批准模板；没有明确资格时不得发送。
输出：汇总候选数、成功数、跳过数、失败数、结果未知数及对应业务 ID。
异常：发送结果未知时不得重试，记录并转人工核验。
```

定时任务的自然语言说明本身不能创造不存在的渠道发送能力。目标员工必须已经绑定对应工具和 SOP。

### 步骤 5：立即执行并检查记录

1. 在任务行尾点击 **立即执行**。
2. 打开 **查看记录**。
3. 确认状态是 succeeded、needs input、incomplete、failed 或 skipped 中的预期结果。
4. 有会话 ID 时点击 **查看会话**。
5. 检查 Harness TaskFrame、SOP、能力调用和产物。

> **截图占位 30｜检查定时任务运行记录**  
> 页面：`http://127.0.0.1:5173/enterprise/scheduled-tasks`  
> 范围：运行记录弹窗和查看会话按钮。  
> 标注：① 计划时间；② 实际状态；③ 错误；④ 查看会话。

> [!WARNING]
> “立即执行”会创建运行记录并增加 `run_count`。测试生产任务前先评估最大次数，优先使用独立测试任务。

## 15. 按钮影响速查表

### 15.1 会直接或间接改变未来模型行为

- SOP 生成和改写的输入、附件、目标区域、模型选择；
- 确认改写并保存；
- 触发意图、说法示例、目标、必需信息、回复规则；
- 节点类型、节点指令、期待用户信息、允许动作；
- 新增/删除节点和连线，编辑迁移条件；
- 工具、技能和知识库的可选/必需引用；
- “通用/仅限 SOP”能力范围；
- 启用、停用、同步、回滚、移除 SOP；
- 渠道挂载员工、默认员工和智能分发；
- 定时任务的任务说明；
- handoff 中的人工“回复并恢复”。

### 15.2 只改变执行或投递

- 渠道扫码、凭证保存、Secret 轮换和断开接入；
- 定时任务启用、暂停、立即执行、计划时间和最大次数；
- 工具探测或测试；
- 步骤超时和重试策略。

### 15.3 不影响模型

- 搜索、筛选、分页、排行；
- 查看版本详情但不回滚；
- 流程图缩放、适应、全屏、拖动画布；
- 展开思考、复制消息；
- 查看会话、附件、执行记录和投递日志；
- 保存弹窗中的取消；
- 拒绝未应用的改写或工具建议。

## 16. 常见误区

### 16.1 “保存只是存草稿”

不一定。当前企业编辑器新建 SOP 时使用 `published`，会直接启用；编辑既有 SOP 时保留原状态。新建 SOP 第一次保存前必须完成校验。

### 16.2 “流程图只是画图”

错误。节点位置是纯 UI，但节点、连线和条件构成实际状态机。

### 16.3 “给 SOP 绑定工具后模型一定调用”

错误。可选工具由模型按需决定；只有标为必需的能力构成完成门槛。

### 16.4 “设为仅限 SOP 后模型自然知道在哪一步调用”

错误。还必须在具体节点显式引用，否则能力不会出现在该步骤的授权清单中。

### 16.5 “智能分发会选择正确 SOP”

不完全正确。智能分发先选择员工；员工内部的 Turn Planner 再从该员工可用 SOP 中选择流程。

### 16.6 “定时任务可以给渠道联系人定时发消息”

错误。普通定时任务没有渠道和收件人字段，只定时唤醒员工执行内部任务。

### 16.7 “渠道日志里能回复客户”

错误。渠道对话和投递日志是只读的。普通回复必须由外部用户先发起，或通过受控业务工具主动发送。

### 16.8 “人工回复会原文直接发送”

错误。“回复并恢复”先把人工文本交回 AgentLoop，最终 assistant 回复才投递。

### 16.9 “有人工接管就等于所有外发都有审批”

错误。handoff 只在 SOP 节点声明时生效，且不是任意工具调用的通用审批门。

## 17. 排障 SOP

### 17.1 SOP 不触发

1. 检查 SOP 是否已启用。
2. 检查是否属于当前员工而非其他员工。
3. 检查触发意图和说法示例是否覆盖用户表达。
4. 检查当前会话是否已有进行中 SOP，Planner 可能优先继续当前流程。
5. 查看 Trace 中 Planner 的候选和决策。
6. 用 `/sop <skill>` 定向测试流程本身，再单独测试自然语言路由。

### 17.2 SOP 触发错误

1. 缩窄触发意图。
2. 在描述中增加不适用边界。
3. 删除与其他 SOP 高度重叠的宽泛示例。
4. 对相似 SOP 明确区分业务对象、动作和前置条件。
5. 重新测试正例和反例。

### 17.3 工具没有调用

1. 检查工具是否启用并绑定当前员工。
2. 检查能力范围是否为“仅限 SOP”。
3. 若是，检查当前节点是否显式引用。
4. 检查引用是可选还是必需。
5. 检查工具 `allowed_skills` 是否允许当前 SOP。
6. 检查参数 Schema 和当前节点指令是否提供足够参数。
7. 查看 Trace 中能力是否为 unavailable 或被撤销。

### 17.4 SOP 卡在追问

1. 检查 `expected_user_info` 是否放入了不必要字段。
2. 检查已有槽位是否使用稳定字段名。
3. 检查节点是否能先通过工具或知识取得信息，而不是提前追问。
4. 检查连线条件是否永远无法满足。

### 17.5 SOP 跳错步骤

1. 检查节点连线方向。
2. 检查条件、标签和优先级。
3. 检查当前保存版本是否为预期版本。
4. 检查同步或回滚是否改变了节点 ID。
5. 查看 Trace 中当前节点和 `next_step_id`；运行时只允许选择已声明迁移。

### 17.6 外部消息没有回复

1. 检查渠道绑定是否 active/connected。
2. 检查机器人凭证或扫码状态。
3. 检查目标员工仍在挂载列表且可用。
4. 检查会话是否进入 handoff 或 awaiting user。
5. 查看渠道对话记录是否收到入站消息。
6. 查看投递日志是 pending、sending 还是 failed。
7. 检查错误和重试次数。
8. 不要在结果未知时通过外部业务工具手动重复发送。

### 17.7 智能分发到错误员工

1. 检查挂载员工是否过多或职责描述重叠。
2. 检查默认员工是否正确。
3. 临时关闭智能分发验证固定员工路径。
4. 使用 `/切换 <员工名>` 手动切换并利用 10 分钟保护窗复测。
5. 检查是否处于 SOP 中；该场景切换阈值更高。

### 17.8 定时任务没有执行

1. 检查任务状态是否 active。
2. 检查时区、日期和时间。
3. 检查最大执行次数是否耗尽。
4. 检查上一轮是否仍运行；`forbid` 会跳过重叠唤醒。
5. 检查目标员工是否仍可用；员工不可用时任务可能失败并暂停。
6. 查看运行记录及 Harness TaskFrame 状态。

## 18. 上线审批清单

### 18.1 SOP 内容

- [ ] 触发意图包含正例和清晰边界；
- [ ] 目标可验证；
- [ ] 必填信息没有过度收集；
- [ ] 每个节点包含动作、成功条件和失败处理；
- [ ] 连线条件明确且可达；
- [ ] 最终节点和转人工路径完整；
- [ ] 回复规则覆盖承诺、隐私和敏感信息。

### 18.2 能力与副作用

- [ ] 工具、技能、知识库均属于当前员工；
- [ ] 高风险能力设为“仅限 SOP”；
- [ ] 仅在正确节点显式引用；
- [ ] 必需和可选引用设置正确；
- [ ] 写操作前有确认或外部审批；
- [ ] 写操作有幂等键；
- [ ] 结果未知时不会自动重试；
- [ ] 工具密钥未写入 SOP 文本。

### 18.3 版本与权限

- [ ] 当前范围是目标员工；
- [ ] 已检查本地与广场版本差异；
- [ ] 新建 SOP 第一次保存会直接启用的风险已确认；
- [ ] 操作者有权限；
- [ ] 已准备回滚版本；
- [ ] 没有覆盖其他员工的定制分支。

### 18.4 测试与观测

- [ ] 正常、边界、失败、拒绝和确认路径均已测试；
- [ ] 自然语言路由和 `/sop` 定向执行均已测试；
- [ ] Trace 中 SOP、节点、能力和结果正确；
- [ ] 租户存在已启用且测试通过的默认模型；
- [ ] 渠道投递日志成功；
- [ ] 历史会话和反馈保留符合预期；
- [ ] 定时任务不会重叠或重复外发。
